MCP 2026-07-28 stateless HTTP, a guarded HTTP boundary, and full JSON Schema input validation. Several defaults change, so review the items marked **behavior change** when upgrading from 0.1.1.

- **Behavior change:** `McpServerInstance.serveHttp()` answers `POST /mcp` with a stateless MCP 2026-07-28 JSON-RPC dispatcher (`initialize`, `ping`, `tools/list`, `tools/call`, `server/discover`) and resolves with the Node `http.Server`. It no longer creates `Mcp-Session-Id` sessions, so `GET /mcp` streams are gone (404). Responses carry `MCP-Protocol-Version: 2026-07-28`, the optional `Mcp-Method` and `Mcp-Name` request headers must match the body, and `/health` reports `protocolVersion` instead of `activeSessions`.
- **Behavior change:** `createHttpApp()` also mounts that endpoint at `POST /mcp` by default and documents it in its OpenAPI output; `enableMcp: false` turns it off and `mcpPath` moves it.
- New `createStatelessMcpDispatcher()` and `McpServerInstance.dispatcher`, `handleFetch()`, `handleNode()` and `getTools()` mount the endpoint in another server. `ToolApp.mountMcpRoute(app, path?, options?)` mounts it on a Hono app, and `ToolApp.serveMcp()` accepts `McpServerOptions` and resolves with the server. `MCP_PROTOCOL_VERSION_2026_07_28` and `McpHeaders` are exported.
- Tool listings include the new `mcp.ttlMs`, `mcp.cacheScope` and `mcp.annotations` metadata, and the stateless endpoint and `getTools()` also list `outputSchema`. `tools/call` results of object-returning tools carry `structuredContent`, and a result can report `status: 'input_required'` with a `continuationToken` and `prompt` (`ToolInputRequiredResult`).
- **Behavior change:** HTTP requests to `createHttpApp()` and `serveHttp()` pass a shared boundary. A request that carries an `Origin` header is rejected with 403 unless that origin is listed in the new `allowedOrigins` option, which is empty by default, so browser clients need it. The new `authToken` option requires `Authorization: Bearer <token>` (`/health` stays public unless `publicHealth: false`), and JSON bodies above `maxBodyBytes` (default 1 MiB) get 413. A REST request body must be a JSON object. `authorizeToolHttpRequest()`, `readToolJsonRequest()`, `readToolNodeJsonRequest()`, `validateToolHttpOptions()` and `ToolHttpError` are exported.
- **Behavior change:** a tool that throws is reported as `Tool execution failed (requestId: <id>)` over MCP and REST instead of with the exception's message. An `api.statusCodes` value that a JSON response cannot carry (outside 200-599, or 204, 205 or 304) throws a `RangeError` instead of producing an invalid response.
- **Behavior change:** plain JSON Schema tool inputs are validated with Ajv against JSON Schema 2020-12, with `ajv-formats` (new dependencies `ajv` and `ajv-formats`), instead of shallow top-level type checks. Enums, formats, nested objects and arrays, `additionalProperties` and the other keywords are enforced now, and a required property that is present but `null` or `""` is no longer reported as missing; its own schema decides. `createJsonSchemaValidator()` is exported, `validateToolInput()` takes optional `components` for `$ref`s, and a callable custom validator uses its `safeParse`, `parse` or `validate` method.
- MCP request bodies are decoded as JSON-RPC 2.0 envelopes before dispatch. An `id` that is not a string, number or null, or `params` that is not an object, is an invalid request (-32600; `"params": null` counts as absent), and `tools/call` without a string `name` is invalid params (-32602).
- **Behavior change:** `executeTool()` always calls `execute(ctx, input)`, as `ToolHandler` declares. Before, it read the handler's source text and called `execute(input, ctx)` unless the first parameter was named `ctx` or `_ctx`. Wrap a handler written input-first with the new `adaptInputFirstHandler()`.
- WebMCP peer bridge: `WebMcpPeerConfig.authToken` is sent as a bearer token, and `createWebMcpPeerApp()` uses the bridge client of `@oa-sdk/peer-transport` when that package can be imported next to `@oa-sdk/tools` (it is not a dependency, and it is not on npm yet). Otherwise the built-in `WebMcpPeerBridgeClient` validates `peers.json`, `/status`, `/tools` and `/call` documents: it drops unknown and wrongly typed peer fields (including `token`), keeps `skillManifest` and the keyed or array form of the status peers, reads a present non-array `allowedTools` (`null` included) as an empty allow-list, and skips malformed tool entries. Only an explicit `PEER_UNAVAILABLE` answer is retried; another 404, 503 or HTTP error ends the call. `webmcp_call` and discovered peer tools reject non-object arguments.
- `@oa-sdk/chunk-stream` and `@oa-sdk/chunk-stream-ui` are no longer declared as optional peer dependencies. `createChunkStreamTools()` imports `@oa-sdk/chunk-stream-ui` only when it builds a stream from `getDocument`; install it yourself for that path, which otherwise fails with `ERR_MODULE_NOT_FOUND`. Neither it nor `@oa-sdk/peer-transport` is bundled into `dist`. The `ChunkStreamToolsOptions` declarations still import types from `@oa-sdk/chunk-stream-ui`, as in 0.1.1, so a project that type-checks libraries (`skipLibCheck: false`) needs it installed too.
