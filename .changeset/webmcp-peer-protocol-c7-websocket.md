---
"@oa-sdk/webmcp-peer": minor
---

The relay now answers every WebSocket upgrade it refuses with an HTTP response that says why, speaks only the `webmcp-peer.v1` subprotocol, tells a peer with its close code whether to come back, ignores a leading byte order mark on every JSON input, and lets go of sockets whose peer vanished (relay protocol spec O-21, O-22, O-23, O-38, O-42). Several of these change what a peer sees, so review the items marked **Behavior change**.

- **Behavior change:** a refused upgrade gets an HTTP response with `Content-Length`, `Connection: close`, `Cache-Control: no-store` and the relay's lifecycle error body (`{error, code?, …}`), then the connection closes. Before, every refusal but a disallowed Origin was a bare reset. The answers are the lifecycle routes': 404 `NOT_FOUND` for a path that is not a socket endpoint, 404 `ROOM_NOT_FOUND`, 410 `ROOM_ROTATED` (with `replacementRoomId`) and 410 `ROOM_EXPIRED` for the room, 401 `PROVIDER_TOKEN_REQUIRED`/`PROVIDER_TOKEN_INVALID` (with a Bearer challenge) for the provider ticket, and, for the client ticket, the status and name an MCP POST of the same token gets: 401 `CLIENT_TOKEN_REQUIRED`/`CLIENT_TOKEN_INVALID`/`SESSION_INVALID`, 403 `CLIENT_APPROVAL_DENIED`, 410 `SESSION_EXPIRED`. A browser's WebSocket API still only sees a failed connection; other clients can tell a wrong ticket from a room that is gone, rotated or expired. A disallowed Origin gets such a refusal too: 403 `ORIGIN_NOT_ALLOWED`, the refusal every other request from it gets.
- **Behavior change:** the relay checks the opening handshake first, before the subprotocol, the path, the room or the ticket: a request that is not an HTTP/1.1 `GET` whose `Upgrade` lists `websocket` and whose `Connection` lists `upgrade`, or whose `Sec-WebSocket-Key` is not 16 bytes of base64, gets 400 `BAD_UPGRADE`, and a `Sec-WebSocket-Version` other than 13 gets 426 `UNSUPPORTED_WEBSOCKET_VERSION` with `Sec-WebSocket-Version: 13` (RFC 6455 §4.2.1, §4.4). Before, the method, HTTP version, `Connection` and key format were not checked, and the version and `Upgrade` were checked only after the room and ticket lookups.
- **Behavior change:** `upgradeWebSocket` no longer throws `BAD_UPGRADE` for a request that is not an opening handshake: it writes the 400 or 426 response itself and returns a stopped socket (`send` returns `closed`, `onClose` runs once after it returns).
- **Behavior change:** an upgrade that does not offer `webmcp-peer.v1` in `Sec-WebSocket-Protocol` is refused with 400 `SUBPROTOCOL_REQUIRED`. Before, the relay answered with the first value offered, whatever it was: an unknown protocol, an empty string, or the `ticket.<token>` credential itself. The codec now selects `webmcp-peer.v1` when it is offered and no subprotocol otherwise; a ticket, an empty value or an unknown value never comes back in a response. The reference provider and `PeerMcpSession` always offer it.
- **Behavior change:** the relay's close codes now say why a socket was closed, and are exported as `WEBMCP_CLOSE_CODES` from `./config` and the package root: 1000 is a final close after the frame that ended the session, 1001 means the relay is going away (its `close()`, which used 1000 before, and the new idle timeout), 1013 a shed the peer may retry, 4001 `SUPERSEDED` a socket another one replaced (a replaced or detached provider socket and the oldest socket past the four-per-ticket cap, both 1000 before), and 4002 `ROOM_EXPIRED` the provider socket of an expired room (1000 before, without a frame). A peer's close frame with the client-only 1010 is answered with 1000 instead of 1010.
- **Behavior change:** the provider reconnects only after a close it may retry: 1001, 1006 (a connection lost without a close frame, or a close that reports no code) and 1013. After 4002 it ends its session as expired (session error `ROOM_EXPIRED`, approval state `expired`), after 4001 it stops with the session error `PEER_SESSION_SUPERSEDED`, and after any other close (1000 whose frame was lost, or a code refusing a frame it sent) with `SIGNALING_CLOSED`, without reconnecting. Before, every close scheduled a reconnect, so a replaced provider kept reclaiming against `ROOM_PROVIDER_ACTIVE`.
- **Behavior change:** `PeerMcpSession` rejects requests with `TRANSPORT_CLOSED` whose `details` are `{ code, reason }` when the transport reports how it closed, so a caller can tell a close worth retrying (1001, 1006, 1013) from a final one. `PeerMcpTransportCallbacks.onClose` now receives that as an optional `PeerMcpTransportClose` (new type), which the WebSocket transport fills from the close event. The session still never reconnects on its own.
- **Behavior change:** `PeerMcpSession` follows the close codes. After a close it may retry (1001, 1006, 1013, or one without a code) the next request connects again on a new WebSocket; before, it reused the closed socket and reported `connected` while every request timed out. After any other close (1000, 4001, 4002, a code refusing a frame it sent) or a frame that ended the session (`session.revoked`, `room.rotated`, `room.expired`, `approval.rejected`, `approval.expired`), requests fail with that `TRANSPORT_CLOSED` (same `details`) or that error instead of connecting again, so a socket replaced with 4001 no longer displaces the one that replaced it; only the caller's `connect()` (or `disconnect()`) starts over. `PeerMcpService.callTool` and `refreshCatalog` connect through the session's requests and follow the same rule. Each connect makes a new transport (a caller's own `transport` is used again), closes the one the connect before made, and ignores that one's late events. `disconnect()` ends a connect in flight with `SESSION_DISCONNECTED` (a transport that connect gets afterwards is closed) instead of leaving it to time out and turn the session `error` after `disconnect()` resolved `idle`. A `connect()` or request made while `disconnect()` runs connects once it has closed the socket, as after an awaited `disconnect()`, so the session holds at most one socket; another `disconnect()` before that connect starts ends it too, and resolves once the socket is closed. Only the callbacks of the connection the session holds, the latest connect's, speak for it, a caller's own `transport` included, which each connect hands new callbacks: what that transport reports through an earlier connect's callbacks, while `disconnect()` closes it or later (a frame that ends the session, a close event that arrives after `close()` returned), no longer leaves the next request failing instead of connecting again, nor ends the connect after it. The `onMessage` the session sets on a caller's own `transport` that has none is the session's, not one connect's: it delivers for whichever connect holds that transport, and for nothing after `disconnect()`. `disconnect()` closes a caller's own `transport` even while a connect is still connecting it, and the transport a connect was replacing; a transport an ended connect gets afterwards is closed unless the connect after it uses it (the caller's own `transport`, or one a factory hands out again), so the next connect is no longer cut off.
- **Behavior change:** the relay ignores one leading byte order mark (U+FEFF) wherever it parses JSON: an MCP POST body, a JSON body route and a provider or client socket's text message (RFC 8259 §8.1). Before, a socket frame that started with one was silently dropped, so an agent's request never got an answer, and an MCP POST got 400 `PARSE_ERROR`. A second mark is still invalid JSON, and invalid UTF-8 is still refused as before.
- **Behavior change:** the relay pings every provider and client socket every 30 s (`WEBSOCKET_PING_INTERVAL_MS`) and closes one it has heard nothing from for 75 s (`WEBSOCKET_IDLE_TIMEOUT_MS`) with 1001. Browser and Node WebSockets answer pings on their own, so only a peer that vanished without closing its connection is affected: a provider that dropped off the network no longer blocks every reclaim of its room until TCP gives up. A socket the relay itself stopped reading (an agent behind on what it asked for) is not closed for its silence. New relay options `webSocketPingIntervalMs` and `webSocketIdleTimeoutMs` and codec options `pingIntervalMs` and `idleTimeoutMs` change the timing; the idle timeout must be longer than the ping interval, or the relay's constructor (and `upgradeWebSocket`) throws a RangeError.
- New exports: `WEBMCP_CLOSE_CODES` (`./config`, root), `WEBSOCKET_PING_INTERVAL_MS`, `WEBSOCKET_IDLE_TIMEOUT_MS` (`./server`, root), `PeerMcpTransportClose` (`./client`, root).
- Protected relay API: new `sendRefusal`, `refuseUpgrade`, `lifecycleRoomRefusal`, `checkUpgradeRoom`, `providerTokenRefusal` and `checkUpgradeTicket`; `checkLifecycleRoom`, `checkProviderToken`, `sendUnauthorized`, `sendRoomRotated` and `sendRoomExpired` are built on them, and `clientTicketError` now types its `message` as the error name.
