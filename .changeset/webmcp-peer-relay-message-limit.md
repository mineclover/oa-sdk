"@oa-sdk/webmcp-peer": minor

A relay message may now be up to `PEER_RELAY_MAX_MESSAGE_BYTES` (256 KiB of UTF-8 JSON, exported from `./config` and the package root) in either direction, whether it arrives as one WebSocket frame or fragmented. Browser and Node WebSocket clients send each message as one frame, and the relay used to close any socket that sent a frame over 128 KiB, which dropped every agent of the room when it was the provider. The relay's inbound WebSocket parser is now a streaming parser that checks each header field as it arrives: a message over the limit, or over 1024 frames (`MAX_WEBSOCKET_MESSAGE_FRAGMENTS`), closes with 1009 before its payload is buffered; protocol violations close with 1002, binary data with 1003, invalid UTF-8 with 1007 and an `onText` exception with 1011. At most 1 MiB (`MAX_WEBSOCKET_OUTBOUND_BUFFER_BYTES`) is queued for a peer that does not read: a message past it is refused with the new send result `'busy'` (nothing queued, socket kept), pongs that do not fit are dropped, and only a queue that stays full for `WEBSOCKET_STALLED_OUTBOUND_TIMEOUT_MS` (30 s) closes the socket with 1013. Half-open peers are destroyed after `WEBSOCKET_CLOSE_TIMEOUT_MS`, `onClose` runs once as soon as a socket stops, `PeerSocket.close` takes an optional close code, and `upgradeWebSocket` takes optional `UpgradeWebSocketOptions`. **Behavior change:** `PeerSocket.send` returns `'sent' | 'too-large' | 'busy' | 'closed'` (`PeerSendResult`) and never closes the receiving socket for a message it cannot send; the relay answers the sender instead and never detaches the provider for agent traffic. Agent requests are limited to `PEER_RELAY_MAX_REQUEST_BYTES` (256 KiB - 1 KiB, as sent and as re-serialized for forwarding), which always leaves room for the relay's `from`/`sessionId` stamp, now applied to every forwarded `mcp` envelope and offer; a larger request gets `REQUEST_TOO_LARGE` (HTTP 413 for `POST /p/:id/mcp` bodies, which used to be cut at 150,000 bytes and reported as `PARSE_ERROR`; `offer.refused` for offers). A full provider queue gets the retryable `PROVIDER_BUSY` (`data.retryable: true`; HTTP 503 with `Retry-After: 1`), a closing provider `PROVIDER_UNAVAILABLE`, and a reply that no longer fits a WebSocket agent `RESULT_TOO_LARGE`. Replies an agent asked for wait in order while it reads slowly instead of closing it, and broadcasts skip an agent that is behind. WebSocket `tools/list`/`server/discover` fall back to the relay's catalog, a pending `approval.request` is sent once per provider socket, `clientLabel` is capped at 256 characters, and a client that resets during an awaiting `customUpgradeHandler` can no longer crash the relay. The relay bounds request ids (1 KiB), pending requests per agent socket (64) and WebSockets per client ticket (4), closes a provider socket that a new one with the same token replaces, answers oversized JSON bodies with 413 `BODY_TOO_LARGE` and non-object or non-UTF-8 bodies with 400 without acting (a lossy decode used to run them with U+FFFD in place of the bad bytes), and drains oversized bodies so the response reaches the client. The provider withholds a `register` frame over `PEER_RELAY_MAX_CATALOG_BYTES` (`CATALOG_TOO_LARGE`, socket kept open), the relay refuses a catalog whose announcement exceeds `PEER_RELAY_MAX_ANNOUNCEMENT_BYTES`, rejections are matched to the register they answer through `registerSeq`, and session error changes always reach subscribers. Catalog hashes include own `__proto__` keys. The agent client refuses a request over the request limit before sending it with `PeerMcpError` code `REQUEST_TOO_LARGE`, retries retryable refusals such as `PROVIDER_BUSY` with backoff within the request's timeout, and no longer leaks unhandled rejections from in-flight HTTP requests, ping replies or CRDT sends.
