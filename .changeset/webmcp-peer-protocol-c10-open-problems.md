The open problems the protocol review left in the relay protocol spec are decided (relay protocol spec O-62 to O-69, chapter 10.1). Several change what an agent or a provider sees, so review the items marked **Behavior change**.

- **Behavior change:** the relay checks a WebSocket `tools/call` without an id as it checks one with an id, and as it already checked one over HTTP: params without a non-empty string `name`, a catalog stamp in `params._meta` that is not the room's, and a tool the room's catalog does not list stop it before the provider. A notification has no one to answer, so one the relay refuses over WebSocket is dropped unanswered (over HTTP it still gets its 400, 409 or 400 under id null). Before, it reached the provider unchecked, and a provider that runs a message without an id could run a call made for another catalog (O-62, R-MCP-020, R-MCP-026, R-MCP-030).
- **Behavior change:** the relay drops a `notifications/tools/list_changed` the provider sends instead of passing it to the agents. That notification is the relay's: it names the `catalogVersion` and `catalogHash` of a catalog the relay took, the stamp it checks every `tools/call` against, and a provider announces its catalog with `register`. The provider's other notifications and requests still reach the approved agents. The reference provider never sent one (O-63, R-SIG-004, R-MCP-041, R-CAT-008).
- **Behavior change:** a room's expiry ends only the tickets still live (pending or approved). A session that was rejected or revoked, or whose approval request expired, before its room expired keeps that state and its `revokedAt` in `GET /p/:id/sessions/:sessionId`; before, the expiry reported every session of the room as `expired` (O-65, R-ROOM-035, R-ROOM-048).
- The relay's credentials are bearer tokens it issues, not OAuth access tokens. This is now a rule of the spec, pinned by a test: its `WWW-Authenticate: Bearer` challenge carries no `resource_metadata`, and it serves no OAuth protected resource metadata (RFC 9728), authorization server metadata (RFC 8414) or OpenID Connect discovery (their `/.well-known/...` paths are 404). An MCP client sends the joined client token as a static `Authorization: Bearer` header and does not start an OAuth flow on a 401. No wire behavior changes (O-66, R-HTTP-019, R-PEER-053).
- **Behavior change:** `PeerMcpSession` takes a message for the answer to one of its requests only as the relay does: `jsonrpc: "2.0"`, a string or number id, and a `result` or `error` member. A provider's request or notification that carries the id of a call in flight no longer ends that call or frees the relay slot the relay still counts for it (O-64, R-PEER-032).
- **Behavior change:** `PeerMcpSession.request()` (and every call made through it) refuses a request whose id, as a string, is the id of one of the session's requests still in flight (waiting for its answer or for a relay slot, or holding a slot after its caller gave up) with `PeerMcpError` `DUPLICATE_REQUEST_ID` (`details: { method, id }`), without sending it, on every transport. `1` and `"1"` are one id here, since the session matches answers by `String(id)`. Before, the second request could take the first one's answer (over Streamable HTTP), or, over a relay socket, the relay's `DUPLICATE_REQUEST_ID` answer to it freed the first request's slot while the relay still counted it (O-64, R-PEER-032, R-PEER-035). A request is in flight, on every transport, from its `request()` call until its answer arrives or its connection ends, which includes its wait before a retry and lasts past its timeout: over Streamable HTTP, whose POST brings the answer, until that POST ends, and over a relay socket or a raw transport whose `send` returns before the answer, until the answer comes. So a request sent under the id of one that timed out is refused until that one's late answer has arrived, where before it could get that answer and lose its own (over Streamable HTTP, and over a raw transport whose `send` returns first), and a request waiting out a retryable refusal keeps its id, where before a request sent under it meanwhile made that request's own retry fail with `DUPLICATE_REQUEST_ID` (R-PEER-032, R-PEER-036). When a connection ends (`disconnect()`, a transport close, a frame that ends the session, a failed connect), every request gives back its id at once, even one whose `send` is still running, and that send, once it settles, touches nothing of a request sent under the id since; before, a request whose `send` was still running when `disconnect()` ran kept its id until that send settled, so a request under it on the reconnected session was refused with `DUPLICATE_REQUEST_ID` (R-PEER-032, R-PEER-045). That holds when the next connection has a transport of its own (each WebSocket and Streamable HTTP transport, a new one from a `transportFactory`). When it uses the same transport again (your own `transport`, or one your `transportFactory` hands out again), such a send may still write its request there, so on that connection the id stays in flight, and the request counts against the relay socket's slots, while the send runs and, once it has gone out, until its answer arrives or that connection ends: a request under the id is refused with `DUPLICATE_REQUEST_ID`, unsent, where before it was sent and got the relay's `DUPLICATE_REQUEST_ID` answer to the late request instead of its own (R-PEER-032, R-PEER-035). A transport error (`onError`) or a `{type:'error'}` frame, which leaves the connection open, still rejects the requests waiting, but no longer gives back their ids and slots: a request sent keeps them until its answer arrives (over Streamable HTTP, until its POST ends), as after its timeout, where before a request sent under its id on the same connection could get its late answer (R-PEER-032, R-PEER-035, R-PEER-038). A transport you reuse across connects should not report an earlier connect's late answers through the next connect's callbacks, which the session cannot tell from that connection's own (R-PEER-031). A request waiting for a connect is ended at once, and gives back its id, by `disconnect()` (or a transport error or close), even while that connect is still getting its transport from a `transportFactory` or the `connect` of the caller's own transport, which cannot be cut short; before, it stayed pending until that returned (for good if it never did, as its timeout starts only once it is connected), and a request under its id on the reconnected session was refused with `DUPLICATE_REQUEST_ID` (R-PEER-045).
- **Behavior change:** `PeerMcpSession.revoke()` sends one POST. Its body names the room id and room epoch only when the session knows them already; it no longer reads the session status or POSTs an `initialize` first to learn an unknown epoch, which the relay does not need (O-67, R-PEER-046).
- **Behavior change:** the `onMessage` a session sets on a caller's `transport` that has none is now one per transport object: it delivers to the session that connected with that transport last, and to none once that session's `disconnect()` let go of it. A `PeerMcpService({ transport })` hands the same transport to every session it makes, so its `connect()`, `disconnect()`, `connect()` now gets the second session the transport's `ready` and answers, instead of a `TRANSPORT_TIMEOUT` while they went to the first session (O-69, R-PEER-031). A connect that `disconnect()` ended does not take it, even when that transport's `connect()` finishes after another session connected with the same transport; before, it took that `onMessage` back, and the other session stayed `connected` while its requests timed out (R-PEER-031, R-PEER-045). Nor does such a connect close that transport while a connection of any session handed it holds it, connected or still connecting; before, it closed it, so the other session stayed `connected` while every request failed, or, when the close was reported with code 1000, ended with `TRANSPORT_CLOSED` and did not connect again (R-PEER-045). A connection that has ended (its connect failed, the transport closed, or a frame ended its session) no longer holds the transport, so such a connect closes the transport it reopened when no live connection holds it; before, a session left on such a connection kept it open, for good once that session was abandoned (one whose `PeerMcpService.connect()` rejected, say) (R-PEER-045).
- **Behavior change:** the provider answers nothing for a request of a connection that has ended or for a `tools/call` whose connection ended while it ran (a revocation, an expiry, a replaced or closed socket, `disconnect()`): the channel either would go on is already closed. The `PEER_SESSION_SUPERSEDED` and `OUTCOME_UNKNOWN` JSON-RPC errors it built for them never reached an agent and are gone, with their −32008 class; the agent learns of such a call from the error the relay ended its request with, and, with an AI run ledger, by calling again under the same `context.requestId`. That error is `SESSION_INVALID` for a revocation over HTTP (by the agent or the host), `ROOM_EXPIRED` or `ROOM_ROTATED` when the relay expired or rotated the room, and `PROVIDER_DISCONNECTED` when the provider socket closed first (the provider's own `disconnect()` or `revokeClient()`, a 4001 replacement, a dropped socket). A call whose connection ended while it waited for the ledger no longer runs, and is not answered from the ledger either: before, one the ledger held as `outcome-unknown` or durable was still answered `RECONCILIATION_REQUIRED` or with the replayed receipt, which went nowhere since its channel was closed. Nor does a call run, get an answer or leave a run behind when host code the provider calls before the host ends its connection with `disconnect()` (or `connect()` or `revokeClient()`, which call it): the host adapter's `getServerInfo`, which the provider asks as it reads the request, or a `subscribeAiRuns` listener told of the call's new run or of its action. Before, such a call still ran. No request of an ended connection is answered now, whatever its method and on either channel (relay socket or DataChannel): the provider checks a request's connection once its answer is ready, so host code it calls while handling the request (the host adapter's `getServerInfo`, or `listTools` for a DataChannel `tools/list` or `server/discover`; the ledger; a `subscribeAiRuns` listener) cannot make it answer a connection that ended meanwhile. Before, a `getServerInfo` that called `disconnect()` still had `ping`, `initialize`, `tools/list`, `server/discover` and an unknown method answered, and a request whose handling threw after its connection ended (a ledger lookup that failed, a host adapter that threw after `disconnect()`) was answered −32603 `Internal error`; none of it reached an agent, since the channel was closed. `PEER_SESSION_SUPERSEDED` stays the provider's session error after a 4001 close (O-68, R-PEER-012, R-PEER-013, R-PEER-016).
- A call the host finished after its connection ended is now accounted for in its AI run unless `disconnect()` cleared the runs: its step (and its receipt's operation) is recorded and its action settled. Before, a session end that keeps the runs (a revocation, an expiry, a 4001 close) left the action in flight for good, so the run could not be rolled back (`AI run still has in-flight actions`) or evicted, and a rollback would not have undone the call. `AiRunController.hasAction(runId, requestId)` is new (O-68, R-PEER-016). A listener of the runs (`subscribeAiRuns`, `AiRunController.subscribe`) that throws no longer changes a call or its run: the controller drops the exception, as the provider does a session listener's, and still tells the other listeners, `clear` included. Before, one that threw as a call registered its action left the call unrun and answered −32603 with its action in flight for good, so the run could not be rolled back; one that threw as the provider settled a call the host ran failed the run with the listener's error and answered −32603 for a committed write, whose operation the run did not record, so a rollback did not undo it; and one that threw as the runs were cleared stopped `disconnect()` before it closed the socket. A listener whose `disconnect()` clears a call's run while the provider records the call now ends the recording there instead of throwing `Unknown AI run` (O-68, R-PEER-016).
