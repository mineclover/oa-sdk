"@oa-sdk/webmcp-peer": minor
---

The relay now refuses requests addressed to a host it does not serve, takes `X-Forwarded-*` only from a proxy it is told to trust, lets an operator allow exactly the browser origins they name, bounds room creation by default, and tells browsers and caches what its responses depend on (relay protocol spec O-24, O-25, O-26, O-27, O-46). Several of these change what a client or a deployment sees, so review the items marked **Behavior change**.

- **Behavior change:** a relay bound to the loopback interface (the default `127.0.0.1`), or one whose `allowedHosts` is configured (options, config file, `ALLOWED_HOSTS`, CLI), refuses an HTTP request or WebSocket upgrade addressed to any other host with 403 `{error:'HOST_NOT_ALLOWED', host}`, before the CORS preflight, the Origin check and every hook. A page whose name a DNS rebinding pointed at a local relay therefore reaches none of its routes, `/health` and the descriptor included. The relay's own `host` and `host:port` and the loopback names are always served; a relay on `0.0.0.0` with no configured list does not check the host. `PeerServerConfig` gains `enforceAllowedHosts`.
- **Behavior change:** a configured `allowedHosts` replaces `DEFAULT_ALLOWED_HOSTS` instead of being merged with it, so a relay that lists `relay.example.com` no longer serves `*.pages.dev`, `*.workers.dev` or `*.trycloudflare.com` hosts.
- **Behavior change:** the relay ignores `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-For` unless they come from a proxy the new `trustProxy` setting trusts (option, config file `trustProxy`, `PEER_SERVER_TRUST_PROXY`, `--trust-proxy`; default `false`). `true` trusts the relay's own peer, one proxy in front of it; a list names trusted proxy addresses and CIDR ranges; any other entry throws `TRUST_PROXY_INVALID`. From a trusted proxy the descriptors' base URL takes the last `X-Forwarded-Proto` (only `http` or `https`) and `X-Forwarded-Host` value, the one the nearest proxy wrote, and the host check applies to that host and to the request's own `Host`: a page DNS rebinding pointed at a loopback relay behind a local tunnel connects from the trusted loopback address too, and could otherwise get past the check by sending `X-Forwarded-Host: localhost`. A proxy that keeps a loopback upstream `Host` or passes the public one on is served; one that rewrites it to another name needs that name in `allowedHosts`. Before, anyone's `X-Forwarded-Host` that matched an allowed host became the descriptor URL and any `X-Forwarded-Proto` became its scheme. A deployment behind a proxy must now set `trustProxy`.
- **Behavior change:** the publish rate limit counts a request against the client address a trusted proxy reports, the first `X-Forwarded-For` address outside the trusted hops, instead of the socket address. Behind a proxy, callers no longer share one bucket, and an address a caller writes ahead of its proxy's cannot pick a fresh one.
- **Behavior change:** a configured `allowedOrigins` (options, config file, `ALLOWED_ORIGINS`, CLI; several are merged) replaces the default policy instead of widening it, and `isOriginAllowed` no longer allows loopback origins and `framebook-storyboard.pages.dev` whatever the list says. `DEFAULT_ALLOWED_ORIGINS` is now `localhost`, `127.0.0.1`, `[::1]` (any scheme and port) and `*.framebook-storyboard.pages.dev`; with the relay's own `http://{host}:{port}` it applies only when no list is configured. A relay that lists `https://app.example` refuses a page on `http://localhost:5173`.
- **Behavior change:** a disallowed Origin gets one refusal everywhere: 403 `{error:'ORIGIN_NOT_ALLOWED', origin}` as JSON with `Content-Length` and `Vary: Origin`, for a CORS preflight (which answered `CORS_ORIGIN_DENIED` before), any other request, and a WebSocket upgrade (which got a bare `text/plain` 403 without `Content-Length` before; it is now an upgrade refusal like the others, with `Connection: close`).
- **Behavior change:** without a publish key, `POST /p` is rate limited by default too: 30 rooms per 60 s per client address (`DEFAULT_PUBLISH_RATE_LIMIT_MAX`). Before, the default was unlimited without a key. Set `publishRateLimitMax: 0` to turn the limit off.
- **Behavior change:** `POST /p/:id/rotate` spends a publish rate-limit unit too, from the publisher's bucket at the caller's address, since it adds the replacement room (relay protocol spec O-61): past the quota it answers 429 `PUBLISH_RATE_LIMITED` (or 503 `PUBLISH_RATE_LIMIT_UNAVAILABLE`) with `Retry-After` and leaves the room as it was, and its 201 names the quota (`X-RateLimit-Limit`, `X-RateLimit-Remaining`). Before, a provider could rotate again and again with each new provider token and fill `maxRooms` in seconds, locking every `POST /p` out until the retained rooms were deleted.
- **Behavior change:** the relay holds at most `maxRooms` rooms (new option, default 10000; `Infinity` for no bound), counting the expired and rotated rooms it retains until they are deleted a day after their expiry. At the bound, `POST /p` and `POST /p/:id/rotate` answer 503 `{error:'ROOM_CAPACITY_EXCEEDED', retryAfterMs}` with `Retry-After`, the time until the first held room is deleted, and change nothing.
- **Behavior change:** a CORS response (a 304 included) carries `Access-Control-Expose-Headers: Retry-After, ETag, X-MCP-Catalog-Version, X-MCP-Catalog-Hash, X-RateLimit-Limit, X-RateLimit-Remaining`, so a browser agent can read the `Retry-After` of `PROVIDER_BUSY` and the rate limit, the `ETag` of a conditional GET and the catalog stamp.
- **Behavior change:** the CORS preflight answers `Access-Control-Allow-Methods: GET, POST, DELETE, OPTIONS` (it listed the unused `PATCH` and left out `DELETE`), and an `OPTIONS` without an Origin gets no `Access-Control-Allow-Origin` (it got `http://{host}:{port}` before).
- **Behavior change:** every relay response names `Vary: Origin` (a cacheable route's own `Vary` includes it), and every JSON response carries `Content-Length` instead of chunked encoding.
- **Behavior change:** the room descriptor (`GET /p/:id/mcp`, 200 and 304) names `Vary: Origin, Accept, Accept-Encoding`, since an `Accept` of only `text/event-stream` gets 405 instead: a shared cache no longer answers an SSE GET with a cached descriptor. `mcpDescriptorCacheHeaders` takes the `Vary` as a new optional fourth argument.
- **Behavior change:** every 405 of `/p/:id/mcp` names `Allow: GET, POST`; the SSE GET's said `Allow: POST`. A relay route asked with a method it does not take now gets 405 `{error:'METHOD_NOT_ALLOWED'}` with the route's `Allow` (`PUT /p/:id/mcp`, `GET /p/:id/join`, `POST /config`, ...) instead of 404, once no `customHttpHandler` took the request; only a path that is no relay route is 404.
- **Behavior change:** `/health`, `/status` and `/ping` report `activeRooms` as the live rooms only (neither expired nor rotated) and the rooms the relay still retains as the new `retainedRooms`. Before, `activeRooms` counted both. `probePeerHealth` passes the new count on as `PeerHealthResult.retainedRooms`.
- Fixed: a `host:port` rule of `allowedOrigins` or `allowedHosts` with an IPv6 literal (`[::1]:4500`) now matches; it was split at the first colon before.
- Protected relay API: new `fromTrustedProxy`, `forwardedHeader`, `clientAddress`, `requestHost`, `hostRefusal`, `isLiveRoom`, `roomCapacityRefusal`, `corsHeaders`, `publisherTokenHash`, `sendPublishRateRefusal` and `publishRateHeaders`; `requestOrigin` and `publishRateIdentity` use them. New public fields `enforceAllowedHosts`, `trustProxy` and `maxRooms`.
