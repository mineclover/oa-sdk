"@oa-sdk/webmcp-peer": minor

MCP JSON-RPC requests are routed by the same rules on the relay's HTTP endpoint and its agent WebSocket, the provider negotiates the MCP revision as the relay does, and `PeerMcpSession` follows the Streamable HTTP client rules and checks the relay's catalog hash (relay protocol spec O-01, O-03, O-28, O-29, O-30, O-31, O-33, O-34, O-36, O-37, O-39, O-41). Several replies change, so review the items marked **Behavior change**.

- **Behavior change:** the provider answers `initialize` on every channel with the revision the relay's HTTP route negotiates: the requested one when it is in `MCP_INITIALIZE_PROTOCOL_VERSIONS`, otherwise `2025-11-25`. Before, it answered `2026-07-28` whatever was asked, a revision without `initialize`. A `server/discover` the relay forwards reports the same negotiation and `supportedProtocolVersions: MCP_INITIALIZE_PROTOCOL_VERSIONS` (it reported `2026-07-28` and `MCP_PROTOCOL_VERSIONS`); over the DataChannel it still reports `2026-07-28`. The relay and the provider share one negotiation function.
- **Behavior change:** the relay's own `server/discover` result (HTTP, and a WebSocket listing the relay answers for the provider) adds `supportedProtocolVersions` (the four initialize-era revisions) and `capabilities` (`tools.listChanged` `false` over HTTP, `true` over WebSocket), so a WebSocket agent gets the same negotiation, revision list and capabilities whether the provider or the relay answers (each still reports its own `serverInfo`).
- **Behavior change:** a WebSocket request with `id: null` is refused with `-32600` `INVALID_REQUEST` (id null) for a ticket in any state and is never forwarded, as over HTTP. Before, an approved ticket's `id: null` request was forwarded as a notification, so a `tools/call` skipped the relay's `CATALOG_CHANGED` and `TOOL_NOT_FOUND` checks and ran on the host. The provider answers an `id: null` request `-32600` `Invalid Request` without running it, and the relay drops a provider reply it cannot match to a request (an id that is null or not a string or a number) instead of broadcasting it to every agent of the room.
- **Behavior change:** every HTTP notification (a message without `id`) the relay accepts gets 202 with an empty body, whatever its method. One of a method the relay answers itself (`ping`, `initialize`, `tools/list`, `server/discover`, `notifications/initialized`) is accepted without the room, ticket and catalog checks; any other is checked as a request is and accepted once the provider takes it, and a refused one gets the status of the check that refused it, such as 404 or 410 for the room, 401, 403 or 410 for the ticket and 503 without a provider, with a JSON-RPC error under id null. Before, an id-less `ping`, `initialize`, `tools/list` or `server/discover` got a 200 JSON reply with id null (or 503 `CATALOG_UNAVAILABLE` for a listing). A message with an id and a `notifications/*` method is a request no MCP server defines and gets `-32600` `INVALID_REQUEST` under its id, over HTTP (400; `notifications/initialized` with an id got 202 before) and over WebSocket (before, it was forwarded to the provider).
- **Behavior change:** over the agent WebSocket the relay answers `ping` itself (`result: {}`) for a ticket in any state, and never forwards it; a ticket waiting for approval got `-32053` `CLIENT_APPROVAL_REQUIRED`. A ticket that is not approved gets the relay's public discovery as an HTTP agent does: `initialize`, `tools/list` and `server/discover` are answered with the relay's results (its `serverInfo`, the room's catalog, `_meta.auth.state` the ticket's status; `CATALOG_UNAVAILABLE` while the room has no catalog) instead of `CLIENT_APPROVAL_REQUIRED`. The WebSocket `initialize` lists the catalog once, in `tools`: its `_meta.bootstrapCatalog` names the catalog (`catalogVersion`, `catalogHash`, `source`) without listing the tools again, so it fits the message limit for every catalog the relay accepts (over HTTP, which has no message limit, the bootstrap catalog still lists them). A relay answer that would still not fit (one a long `serverName` grows) gets `-32603` `RESULT_TOO_LARGE` instead of being dropped. An approved ticket's `initialize` and listings still reach the provider, so its listings still update the room catalog.
- **Behavior change:** every WebSocket listing result carries the relay's `catalogVersion` and `catalogHash` in `result._meta`, where every HTTP listing has them, whether or not the agent sent `_meta`; a provider's own `result._meta` members are kept. The same members at the top of `result`, for an agent that sent `_meta`, are deprecated and stay for one minor release. A listing the relay answers itself has the HTTP route's whole listing metadata in `result._meta`. The 2 KiB below the message limit still holds a listing of the largest catalog the relay accepts under the longest request id.
- **Behavior change:** a room whose provider registered an empty catalog lists `tools: []` over HTTP (`tools/list`, `server/discover`, `GET /p/:id/mcp/tools`), as over WebSocket; it got 503 `CATALOG_UNAVAILABLE`. Only a room with neither its own nor a deployment catalog is unavailable, and the 503 body of `GET /p/:id/mcp/tools` and `GET /mcp/catalog` reports the snapshot's `catalogVersion`.
- **Behavior change:** an agent socket's 64 pending requests (`TOO_MANY_PENDING_REQUESTS`) count the requests waiting for the provider and the replies waiting for the agent to read them, not the other frames the relay holds for a slow agent (`approval.pending`, `approval.approved`, `ready`, `offer.refused`). Before, those frames could make the relay refuse a request the agent counted as its 64th.
- **Behavior change:** while frames wait for an agent that is behind, the relay handles nothing more from it, not even the frames of a read it already took: the codec (`upgradeWebSocket`) handles no frame while its owner has the socket paused and keeps the rest of the read for when it resumes. Before, a read's every frame was handled, so an agent waiting for approval that never read could ask for hundreds of catalog listings in one write and make the relay hold a copy of the catalog for each. What waits for one agent is now the replies to its requests in flight, the answer to the one frame the relay was handling and a few frames of its own, and every listing shares the relay's one catalog, which the relay now holds frozen, instead of a copy.
- **Behavior change:** `PeerMcpSession` checks a catalog's `catalogHash` against its tools (the relay hashes them with the same function). A listing or announcement whose hash does not match is refused with `CATALOG_INTEGRITY_UNVERIFIED` and the cached catalog stays; before, the client took the relay's hash as it was.
- **Behavior change:** the Streamable HTTP transport of `PeerMcpSession` sends `Accept: application/json, text/event-stream` and reads a `text/event-stream` response; `initialize()` ends with a `notifications/initialized` notification, and every later request carries the negotiated revision as `MCP-Protocol-Version` (until `disconnect()`). A non-2xx JSON-RPC error with a `Retry-After` header carries the delay as `retryAfterMs`, and a retryable refusal waits `max(backoff, retryAfterMs)` before it is sent again: the relay's `PROVIDER_BUSY` (`Retry-After: 1`) is retried after 1 s, not 100 ms.
- The spec now states as normative what the relay already did: a request refused before it reached the provider gets its HTTP status, and the result of one the relay forwarded (the provider's answer, or `MCP_REQUEST_TIMEOUT`, `PROVIDER_DISCONNECTED`, `ROOM_ROTATED`, `ROOM_EXPIRED`, `SESSION_INVALID`) comes with 200 and a JSON-RPC body, so an agent judges by the JSON-RPC `error`; each transport measures the request limit on what it carries (the `mcp` envelope over WebSocket, the body over HTTP), and an HTTP 413 before parsing has id null; HTTP requests are not counted per agent and a duplicate id is forwarded under a rewritten wire id; `-32027` `SOURCE_CHANGED`/`RUNTIME_EPOCH_MISMATCH` and `CATALOG_STALE` are reserved names this relay and provider never send, and `_meta.runtimeEpoch` is information neither reads.
- Protected relay API: `mcpInitializeResult` takes the transport it answers on (`'http'` or `'websocket'`) as its last argument; `mcpCatalogSnapshot` returns the catalog the relay holds, frozen, instead of a copy; new internal `freezeToolCatalog` in `src/server/deployment-catalog.ts`. `mcpDiscoverResult` takes a `listChanged` argument, `relayCatalogListing` takes the listing (`method`, `includeCatalogMeta`, `protocolVersion`, `ticketStatus`) and the snapshot instead of the tools and the pending request, `mcpCatalogSnapshot` reports `available`, and there are new protected `mcpToolsListResult`, `mcpInitializeResult`, `catalogStamp` and `answerAgentMetadata`.
