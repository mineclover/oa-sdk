"@oa-sdk/webmcp-peer": minor
---

A provider can no longer speak for the relay to its agents, an agent behind on its replies gets them before the frame that ends its session, the register budget also bounds catalogs that change, the provider relies on one ticket per room, auto-reconnect neither enables writes nobody enabled nor opens a room nobody asked for, the DataChannel framing has one rule in both directions, and an offer has a contract the relay enforces (relay protocol spec O-20, O-35, O-40, O-43, O-44, O-45, O-58). Several of these change what a peer sees, so review the items marked **Behavior change**.

- **Behavior change:** the relay passes on from the provider socket only a JSON-RPC notification or request in an `mcp` frame, to the sockets of an approved ticket, and `answer`/`release`, to the one socket whose offer they name. Every other provider frame is dropped: the relay's own types (`ready`, `error`, `pong`, `session.*`, `room.*`, `approval.*`, `offer.refused`), `ice`, unknown types and an `mcp` frame without a JSON-RPC message. Before, all of them went to every agent socket of the room, pending tickets included, so a provider could rebind a `PeerMcpSession`'s session id with `ready`, fail its calls with `error` or end it with `session.revoked`, and every agent got another agent's `answer`.
- **Behavior change:** a provider notification no longer reaches the sockets of a ticket that waits for approval. The relay's own `list_changed` and catalog announcements still go to every socket of the room.
- **Behavior change:** the frames that end an agent's session (`approval.rejected`, `approval.expired`, `session.revoked`, `room.rotated`, `room.expired`) go through the socket's outbox, and the socket closes (1000) once everything waiting has gone out. The agent gets the replies queued before the end first, a `tools/call` result that ran included, then the end frame, then the errors of its requests in flight, then the close. Before, the end frame was a plain send that a full queue dropped or that overtook the waiting replies, and the close threw the waiting replies away, so a slow agent could get a bare 1000. The socket leaves the room at once, so it gets no broadcast meanwhile; an agent that reads nothing is still closed by the 30 s stall close (1013).
- **Behavior change:** every `register` evaluation uses the room's budget (8 at once, then one a second), a catalog the relay takes included. Before, a taken catalog gave its evaluation back, so a provider alternating two catalogs made the relay normalize, hash, version and broadcast (up to 260096 bytes per agent) at the rate it sent. The waiting frame is still replaced by the next one and the last frame is always evaluated, so a provider's latest catalog is still announced, later.
- **Behavior change:** while the room holds a catalog (the room's or the deployment's), the relay answers a WebSocket agent's whole-catalog `tools/list` and `server/discover` from its own catalog, as the HTTP route does, without evaluating the provider's reply. It takes a catalog from a listing reply only in a room that holds none. Before, a listing reply could replace the room catalog, without budget. A WebSocket `server/discover` of an approved agent in a room with a catalog now reports the relay's `serverInfo`, not the provider's.
- **Behavior change:** the provider serves a request on the relay socket only for the session it approved: one whose relay-stamped `sessionId` is another session's, or missing, is answered −32053 `CLIENT_APPROVAL_REQUIRED` and not run. The relay issues one ticket per room epoch, which the spec now fixes as a protocol invariant, and always stamps the session, so nothing a conforming relay forwards is refused.
- **Behavior change:** the provider's `setWriteEnabled()` and `toggleWrite()` save the state the host reports to localStorage `webmcp:write-enabled`, and auto-reconnect enables writes only when that value is `"true"`, the rule `connect()` already used. Before, nothing saved the key and auto-reconnect enabled writes whenever it was not exactly `"false"`, so a reconnect turned on writes the user never enabled.
- **Behavior change:** auto-reconnect only reclaims the saved room. When the relay refuses the saved lease (400, 401, 403, 404, 410, or a 409 other than `ROOM_PROVIDER_ACTIVE`), the provider forgets the lease and stops at state `error` with the session error `ROOM_LEASE_LOST`, without opening a new room or scheduling another attempt; the host opens a new invite with `connect()`. A reclaim that fails otherwise (a 5xx, say) keeps the lease and is retried with backoff. With no saved lease for the saved relay, auto-reconnect does not run, so reloading the host page no longer opens a room by itself. Before, every one of these cases created a new room with a new invite URL and left the agent on the old room.
- **Behavior change:** a reclaim refused with 401 or with a 409 other than `ROOM_PROVIDER_ACTIVE` (such as `ROOM_LEASE_BINDING_INVALID`) also clears the saved lease for a host's `connect({ reclaimLease: true })`, which still falls back to `POST /p`.
- **Behavior change:** the provider sends a DataChannel frame in at most 512 chunks of 2048 UTF-16 code units, the framing it accepts (at most 512 chunks of at most 16384 units), so a frame is at most 1048576 code units. A larger reply is replaced with RESULT_TOO_LARGE (a `tools/call` result with `isError` and `error.code: "RESULT_TOO_LARGE"`, any other reply the JSON-RPC error with `data: { limitCodeUnits: 1048576 }`), and any other larger frame (`grant`, `crdt`) is not sent and is logged. Before, the provider sent any number of chunks, which a peer of the same framing refused past 1048576 units.
- **Behavior change:** the relay requires an offer's `requestId` to be a non-empty string of at most 1 KiB of JSON. Without one it refuses the offer with `offer.refused` −32600 `INVALID_REQUEST`, without a `requestId`, instead of forwarding it (a longer one stays `REQUEST_ID_TOO_LARGE`). An agent socket has at most one offer waiting for its answer: another is refused with −32087 `TOO_MANY_PENDING_REQUESTS` `{ limit: 1 }`, and a `requestId` another socket of the room uses with −32600 `DUPLICATE_REQUEST_ID`, both echoing the `requestId`. An offer the provider does not answer within `mcpRequestTimeoutMs` is refused with −32001 `MCP_REQUEST_TIMEOUT`, and one whose provider socket goes away with −32001 `PROVIDER_DISCONNECTED`; a late answer is dropped. `offer.refused` is no longer built from the frame type.
- **Behavior change:** the provider answers only an offer with a non-empty string `requestId`, under that id; before, it answered one without it under the last approval request's id. The DataChannel's `grant` and the relay `release` name the offer the provider answered on that peer connection, not the approval request, so the relay can route the release to the socket that offered.
- The spec now marks the DataChannel handoff (offer, answer, `hello`, `grant`, `release`) as experimental and implemented by the provider only, records that agents of the room get `PROVIDER_UNAVAILABLE` after a release, and states that the protocol has no trickle ICE (`ice` frames are dropped in both directions).
- Protected relay API: `broadcastToAgents(entry, frame, { approvedOnly })` takes an options argument; new protected `closeAgentSocket`, `detachClientSocket`, `forwardOffer`, `offerSocket`, `dropOfferRoute`, `deliverOfferOutcome` and `failOffersForProvider`. `failPendingForProvider` also refuses the offers waiting for the provider.
