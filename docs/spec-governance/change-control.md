# 공식 기준 변경 및 충돌 처리

## 표준 변경 절차

1. **분류** — 문서, 구현 현황, 계약, 계획, 릴리스 중 하나로 분류한다.
2. **정본 확인** — `.ai/spec-loader.yaml`과 이 디렉터리의 정본 표에서 소유 파일을
   확인한다.
3. **최소 변경** — 정본을 먼저 변경하고, 파생 문서·snapshot·매핑은 필요한 범위만
   갱신한다.
4. **영향 확인** — 소비 package, 사용자 가이드, generated artifact, version channel을
   확인한다.
5. **검증 실행** — [`document-policy.md`](./document-policy.md)의 변경 종류별 최소
   게이트를 실행한다.
6. **기록** — 공식 기준을 바꿨다면 아래 네 항목을 [`decision-log.md`](./decision-log.md)에
   추가한다.
   - 변경 내용
   - 변경 이유
   - 영향 범위
   - 정본·파생 자료의 저장 위치
7. **검토** — 계획 문서의 완료 항목은 `spec.md`와 테스트 매핑으로 승격되었는지 확인한다.

## 예외

예외는 편의를 위한 영구 규칙이 아니다. 다음을 모두 기록할 때만 허용한다.

- 예외가 필요한 구체적 사실과 정상 경로가 실패하는 이유
- 적용 범위(파일, package, bundle 또는 기간)
- 보상 검증과 사용자/consumer 영향
- 종료 조건 또는 재검토 날짜
- 승인된 저장 위치와 담당자

TypeSpec의 `accepted-restored-drift.json`처럼 도구가 요구하는 예외는 정확한 값과 hash를
고정하고, snapshot 승격과 함께 검토한다. 예외를 숨기기 위해 generated artifact를 직접
수정하지 않는다.

## 충돌

다음 유형을 구분한다.

- **문서 충돌**: 두 문서가 같은 사실을 다르게 설명한다. 정본을 하나 선택하고 나머지는
  링크·요약으로 바꾼다.
- **코드-문서 충돌**: 코드/테스트와 SSOT가 다르다. 현재 동작을 증거로 기록하되,
  의도된 계약인지 버그인지 결정한 뒤 SSOT와 검증을 함께 갱신한다.
- **정본-생성물 drift**: source와 artifact가 다르다. 원천에서 재생성하고 diff를
  검토한다. snapshot을 직접 고쳐 drift를 숨기지 않는다.
- **외부 표준 충돌**: 적용 표준의 버전과 해석을 명시하고, 호환 계층이나 예외를
  결정 기록에 남긴다.

해결 전에는 충돌 상태를 `planned` 또는 `blocked`로 표시하며, 상충하는 주장을 동시에
`active` 정본으로 유지하지 않는다.
