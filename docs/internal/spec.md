## 패키지 구조

```
Core Platform
  core                        공유 기반 유틸리티
  openapi-projection-contract 외부 schema producer projection 경계
  typespec-decorators      production TypeSpec extension helper와 provenance 경계
  schemas                     TypeSpec/OpenAPI schema SSOT와 artifact
  parser                      OAS 3.2 파서, IR, ref, lint, validate, query
  codegen                     build, 변환, governance CLI와 typegen
  spec-lens                   revision, diff, timeline, provenance 관측
  spec-lens-contract          spec-lens browser-safe HTTP wire contract
  ast-sync                    TypeScript AST 양방향 동기화와 독립형 타입 가드
  tools                       TypeSpec JSON Schema 기반 MCP/CLI 도구 브릿지

Downstream Integration
  router                      Hono/Express typed stub
  client                      typed fetch SDK와 SSE
  mock-server                 AJV mock engine, adapter, test helper
  chunk-stream                bounded chunk stream primitives
  chunk-stream-crdt           CRDT chunk merge and state helpers
  chunk-stream-ui             UI playback and action bridges
  chunk-stream-timeseries     time-series chunk adapters
  chunk-stream-react          React hooks and playback synchronization
  peer-transport              authenticated packet transport and bridge client
  peer-server                 peer registry, signaling, and RPC dispatch
  collab-workspace             bounded Tree-Lattice workspace and intent locks
  mcp-mesh                    validated domain/session tool mesh and CLI

Maintenance-only
  dpm, personas, typia-mock, logical-erd-contract, typespec-erd, ttsc-compile-fixture

Apps and references
  nestjs-ref, playground, preview, spec-lens-ui
```

Core Platform은 schema/spec 관리 방향을 소유한다. Downstream은 그 계약을 소비해 검증하지만
Core 자체는 아니다. Maintenance-only는 security, compatibility, migration만 허용하며 새 기능은
scope-reactivation decision이 필요하다. Markdown editor와 GitLab agent operations 제품은 각각
`markdown-editor`, `gitlab-agent-ops` 독립 저장소가 소유한다.

안정화 lane은 Node.js 24 LTS와 TypeScript 5.9.3을 사용하며, 기본 CI와 `.nvmrc`도 이 lane을
기준으로 한다. Node.js 26 Current 호환성 lane은 TypeScript 7.0.2와 `ttsc` 0.26.0으로 Core
TypeScript source와 생성 선언을 no-emit으로 검사한다. Current 릴리스는 운영
build/declaration emission을 대체하지 않으며 `.nvmrc.latest`로 선택하는 선행 호환성 검증 lane이다.
`packageManager`는 pnpm 10.30.3으로 고정하고, Corepack으로 실행한다. Node 타입 의존성은 지원
baseline과 맞춘다.

## 기능별 테스트 관리 ✅

`docs/internal/feature-test-matrix.json`은 기능과 대표 테스트 경로, 유지 명령을 연결하는
machine-readable SSOT다. 사람이 읽는 요약은
[`feature-test-matrix.md`](./feature-test-matrix.md)에 둔다.

현재 매핑은 51개 기능 그룹과 CLI spec drift guard를 포함한 테스트 경로 패턴을 관리한다.

```bash
pnpm check:feature-tests
```

이 검증은 중복 feature id, 필수 필드 누락, 존재하지 않는 테스트 파일, 매칭되지 않는 glob,
테스트 경로나 명령이 비어 있는 feature를 실패로 처리한다.

## 외부 OpenAPI Projection Producer 소비 ✅

bun-graph-db는 OA SDK 바깥의 OpenAPI projection producer로 소비할 수 있다.
상세 워크플로는 [`bun-graph-db projection 소비`](../guides/use-cases/bun-graph-db-projections.md)에 둔다.

| Artifact | Source | OA SDK use |
|---|---|---|
| Static full document | `GET /api/openapi` | stable REST/MCP endpoint discovery, `validate`, `typegen`, `client`, mock-server |
| Table component bundle | REST/GraphQL/MCP table projection with `profile=component-bundle` | runtime table reusable schema snapshot |
| Table operation contract | REST/GraphQL/MCP table projection with `profile=operation-contract` | runtime table create/update request contract, table-specific generated types/client/mock |

Static full documents are stable endpoint contracts. Runtime table shapes stay
projection snapshots and must be stored with their `versionHash` freshness
marker.

Schema/property `description`, JSON-compatible `default`, `example`/`examples`, `deprecated`, `additionalProperties: false` sealing, tag metadata, response headers, and bearer security requirements are emitted through TypeSpec-native constructs. Parameter/request body media/response media examples와 unsupported security component metadata는 generated bundle에서는 sidecar에 남겨 mock/runtime semantics를 보존하고, sidecar-less authored bundle에서는 TypeSpec `@extension(...)`이 만든 `x-oa-sdk-components`, `x-oa-sdk-info`, `x-oa-sdk-operation-component-refs`, `x-oa-sdk-operation-examples`, `x-oa-sdk-operation-security`, 및 `x-oa-sdk-security-schemes` metadata로 보존할 수 있다. Request body examples는 `oa-sdk.typespec-extensions.v5` manifest에서, explicit public operation security override는 `oa-sdk.typespec-extensions.v5` manifest에서, root info metadata는 `oa-sdk.typespec-extensions.v5` manifest에서, reusable parameter/response component identity는 `oa-sdk.typespec-extensions.v5` manifest에서 restore-bearing extension semantics로 인정한다. Sidecar 또는 extension-owned `example`/`examples` 타깃은 복원 시 기존 TypeSpec-emitted example과 병합하지 않고 OA SDK 값을 적용해 재추출 안정성을 유지한다. 라운드트립 평가는 `pnpm typespec:roundtrip`이 export → TypeSpec OpenAPI emitter → sidecar restore/re-extract → OA SDK validate → OA SDK diff를 실행하고, `pnpm typespec:bundle-check`는 같은 bundle check 구현을 호출하는 repo wrapper로 유지한다. `pnpm typespec:sidecar-to-extensions`는 지원되는 compatibility sidecar entry를 TypeSpec `@extension(...)` snippet으로 변환하고, 미지원 entry는 residual sidecar와 report에 명시한다. ### Definition duplicate-review command (OpenAPI aggregation governance Phase 2)

`oa-gen duplicate-review --fragments <dir> --format markdown|json`은 Definition Builder fragments를 읽어 duplicate canonical id, 동일 content hash 후보, 같은 local name의 다른 shape, target-local output name collision, explicit `metadata.semanticAliasOf` pair를 리포트한다. 기본 format은 PR comment용 compact Markdown이고 JSON schema는 `oa-gen.duplicate-review.v1`이다. `--target <config>`은 반복 지정 가능하며, output-name 검사는 지정된 실제 target마다 수행한다.

JSON report는 `findings[].sources[]`마다 `canonicalId`, `sourcePath`, `sourcePointer`, `contentHash`를 보존한다. Semantic alias는 해당 source/target pair가 같은 content hash group에 있을 때만 same-content 후보에서 alias source를 제외하고, 같은 hash를 공유하는 다른 canonical id 후보는 계속 보고한다.

정책은 탐지와 실패 기준을 분리한다. 기본 `--policy report`는 전체 후보를 탐색하지만 `--fail-on none`으로 항상 exit 0이며, target이 없을 때의 synthetic all-fragments naming 결과도 진단용으로만 쓴다. `--policy review`는 모든 후보를 보고 기본 `--fail-on error`로 canonical id와 실제 target output-name collision을 차단하며, 나머지 finding은 `COMMENT`로 남긴다. `--policy ci`는 적어도 하나의 `--target`을 요구하고 기본 검사를 canonical id와 실제 target output-name collision로 한정해 안정적인 gate를 제공한다. `--check canonical-id|content-hash|local-name|output-name|semantic-alias`는 반복 지정해 활성 검사를 대체하고, `--fail-on none|error|warning|info`로 severity threshold를 재정의할 수 있다. JSON에는 적용된 `policy`와 `decision`(`APPROVE`/`COMMENT`/`REQUEST_CHANGES`)이 함께 기록되며, review-bundle은 finding 수가 아니라 이 decision을 사용한다.

구현은 `packages/codegen/src/cli/lib/duplicate-review.ts`와 `packages/codegen/src/cli/commands/duplicate-review.ts`에 있으며, CLI governance manifest는 `packages/codegen/src/cli/spec/oa-gen-governance.ts`와 `docs/cli-spec/oa-gen.governance.json`이 함께 소유한다. 운영 사용법과 문서 갱신 경계는 [Duplicate Review 가이드](../guides/duplicate-review.md)에 둔다.

대표 검증은 `packages/codegen/src/__tests__/duplicate-review.test.ts`와 `packages/codegen/src/__tests__/cli-duplicate-review.test.ts`가 맡는다.

### Target-check command (OpenAPI aggregation governance Phase 3)

`oa-gen target-check --target <target.yaml> --must-include-path <path> --must-exclude-path <path>`은 Definition Builder target config를 `build-spec`의 in-memory output으로 materialize한 뒤 emitted OpenAPI `paths` key를 검증한다. Generated artifact mode는 `--artifact <openapi.yaml|json>`으로 같은 assertion core를 사용한다. `--target`과 `--artifact`는 one-of source mode이며, target mode에서만 `--fragments`가 target sibling `../fragments` 기본값을 override한다.

`--must-include-path`와 `--must-exclude-path`는 반복 가능하고, 중복 제거 후 path 문자열 기준 stable sort로 평가한다. JSON report schema는 `oa-gen.target-coverage.v1`이고, Markdown report는 every assertion row를 `PASS`/`FAIL`로 렌더링한 뒤 failure table을 별도로 제공한다. Missing required path는 `target-coverage/missing-required-path`, emitted forbidden path는 `target-coverage/forbidden-path-emitted` failure code로 non-zero exit한다.

구현은 `packages/codegen/src/cli/lib/target-coverage.ts`와 `packages/codegen/src/cli/commands/target-check.ts`에 있으며, CLI governance manifest는 `packages/codegen/src/cli/spec/oa-gen-governance.ts`와 `docs/cli-spec/oa-gen.governance.json`이 함께 소유한다.

대표 검증은 `packages/codegen/src/__tests__/target-coverage.test.ts`와 `packages/codegen/src/__tests__/cli-target-check.test.ts`가 맡는다.

### Source adapter boundary (OpenAPI aggregation governance source adapter phase)

Codegen source adapters normalize source-specific schema inputs into `OpenApiSourceFragment` values with stable `kind`, `sourcePath`, `sourcePointer`, `contentHash`, `content`, and metadata fields. Shared fragment identity, content hashing, and OpenAPI document section collection live in `packages/codegen/src/cli/lib/openapi-source-fragments.ts`; file readers and YAML/JSON source-location indexes stay in `packages/codegen/src/cli/lib/definition-fragments.ts`.

`packages/codegen/src/cli/lib/source-adapters.ts` adds thin value adapters for Zod schema maps, Drizzle table schema projections, shared OpenAPI Projection envelopes, and Python `ContractSpec` snapshot JSON. `CodegenSourceAdapterRegistry` is the public composition boundary: applications explicitly register trusted adapters, so adapter modules are never dynamically loaded from contract configuration. Zod and Drizzle adapters reuse the existing `zodToSchema()` and Drizzle `convertTables()` conversion paths so existing codegen output remains backward compatible. Projection envelope adapters preserve envelope fields such as `profile`, `versionHash`, `sources`, `refs`, `diagnostics`, `typeTargets`, and root `x-schema-engine-*` extension metadata on emitted source fragment metadata. Python snapshot handling accepts plain JSON mappings, including `{ format: "oa-contract-snapshot", contract: ... }`, and does not import or execute Python runtime code from TypeScript packages.

대표 검증은 `packages/codegen/src/__tests__/codegen-source-adapters.test.ts`, `packages/codegen/src/__tests__/source-file-adapters.test.ts`, and `packages/codegen/src/__tests__/openapi-source-fragments.test.ts`가 맡는다.

### Runtime OpenAPI URL drift input (OpenAPI aggregation governance Phase 4)

`oa-gen drift`는 기존 file path 입력 `--runtime-openapi`와 함께 URL 입력 `--runtime-openapi-url`을 지원한다. 두 입력은 one-of 관계이며 `--managed-openapi`는 기존처럼 관리 OpenAPI YAML/JSON 파일을 받는다.

```bash
oa-gen drift \
  --runtime-openapi-url http://localhost:3000/openapi.json \
  --managed-openapi packages/schemas/src/.merged.yaml \
  --format json
```

인증이 필요한 URL에는 `--runtime-header "Authorization: Bearer $TOKEN"` 같은 header option을 반복해서 전달할 수 있다. URL fetch 결과는 JSON report의 `runtimeFetch`에 `url`, `finalUrl`, `redirected`, `status`, `statusText`, `contentType`, `requestHeaders`를 기록한다. `requestHeaders`에는 header 이름만 남기고 값은 남기지 않는다. URL fetch, non-2xx response, 또는 parse 실패는 `status: "drift-check-failed"`와 `failure.code: "drift-check-failed"`로 보고하고 non-zero로 종료한다. 기존 file path 비교 동작은 변경하지 않는다.

대표 검증은 `packages/codegen/src/__tests__/runtime-openapi-fetch.test.ts`와 `packages/codegen/src/__tests__/cli-scenarios.test.ts`가 맡는다.

### Review-bundle command (OpenAPI aggregation governance Phase 5)

`oa-gen review-bundle --base <base.yaml> --head <head.yaml> --artifact <artifact.yaml> --format markdown|json`은 PR 리뷰용 단일 bundle을 출력한다. 필수 입력은 base/head OpenAPI 문서와 generated artifact이며, artifact freshness는 항상 별도 section으로 포함된다.

선택 입력은 `--inventory`(head OpenAPI inventory 생성), `--runtime-drift <drift.json>`(`oa-gen drift --format json` 출력 포함), `--base-provenance <base-provenance.json>`, `--head-provenance <head-provenance.json>`, `--composition-report <composition.json>`(`build-spec --composition-report` 출력 포함), `--metadata-registry <metadata.json>`(`build-spec --metadata-registry` 출력 포함), `--base-metadata-registry <base-metadata.json>`, `--head-metadata-registry <head-metadata.json>`, `--duplicate-review <duplicate-review.json>`(`oa-gen duplicate-review --format json` 출력 포함), `--typespec-provenance <typespec.json>`와 `--ttsc-provenance <ttsc.json>`(반드시 함께 지정), `--behavior-log <behavior.jsonl>`, `--behavior-db <behavior.sqlite>`이다. 마지막 provenance pair는 TypeSpec 계약 선언과 ttsc 구현 관찰을 OpenAPI pointer로 조인한 review-only evidence이며, recommendation 정책이나 TypeSpec 계약 권한을 바꾸지 않는다. Markdown은 `Recommendation: **...**`와 summary로 시작하고 breaking changes section을 non-breaking changes section보다 먼저 렌더링한다. JSON schema는 `oa-gen.review-bundle.v1`이며 `sections.artifactFreshness`, `sections.runtimeDrift`, `sections.provenanceDiff`, `sections.inventory`, `sections.composition`, `sections.metadataRegistry`, `sections.metadataRegistryDiff`, `sections.duplicateReview`, `sections.parallelEvidence` 아래에 각 원본 report 또는 조인 evidence를 중첩 보존하고, optional behavior recorder는 bundle recommendation과 summary를 append-only behavior record로 남길 수 있다.

`REQUEST_CHANGES` recommendation만 non-zero exit이며 `APPROVE`와 `COMMENT`는 PR comment workflow에서 계속 사용할 수 있도록 exit code 0이다.

`oa-gen parallel-evidence --typespec-provenance <typespec.json> --ttsc-provenance <ttsc.json> --baseline <previous-report-or-metrics.json> --format markdown|json`은 두 provenance artifact의 exact OpenAPI pointer join을 독립 metric report로 출력한다. `oa-sdk.parallel-evidence-metrics.v1`은 pointer coverage, declaration/emission breadth, relation target resolution, ttsc projection class와 feature histogram을 포함한다. baseline delta는 sorted numeric metric map으로 표현하며, 해당 command와 review-bundle의 parallel evidence는 어떤 failure threshold도 강제하지 않는다. 저장/추세 관리와 정책 판단은 CI artifact store 또는 review-bundle behavior record 소비자가 맡고, TypeSpec만 계약 권한을 유지한다.

구현은 `packages/codegen/src/cli/lib/review-bundle.ts`와 `packages/codegen/src/cli/commands/review-bundle.ts`가 맡고, artifact freshness orchestration은 `packages/codegen/src/cli/lib/artifact-review.ts`, sidecar diff summary는 `packages/codegen/src/cli/lib/review-sidecar-diff.ts`, recommendation 판단은 `packages/codegen/src/cli/lib/review-policy.ts`, Markdown section 렌더링은 `packages/codegen/src/cli/lib/review-markdown.ts`, behavior persistence boundary는 `packages/codegen/src/cli/lib/behavior-recorder.ts`를 재사용한다. CLI governance manifest는 `packages/codegen/src/cli/spec/oa-gen-governance.ts`와 `docs/cli-spec/oa-gen.governance.json`이 함께 소유한다.

대표 검증은 `packages/codegen/src/__tests__/review-bundle.test.ts`와 `packages/codegen/src/__tests__/cli-review-bundle.test.ts`가 맡는다.

### External OpenAPI artifact governance scaffold

`oa-gen scaffold-governance --root <service> --service <name> --profile <generic|nestjs-swagger|fastapi> [--source-command "..."] [--runtime-openapi-url "https://..."] [--oa-gen-command "oa-gen"] [--oa-gen-setup-command "..."]`은 외부 프레임워크(NestJS Swagger, FastAPI 등) 산출물을 oa-sdk 기능별 artifact interface로 연결한다. scaffold는 `openapi-governance.config.json`(`oa-gen.openapi-governance.v2` schema의 artifact interface, consumer 매핑, 독립 CLI/CI baseline 정책), `scripts/openapi-governance.sh`(collect/check/review/review-bundle/typegen/inventory/validate-upgraded/drift/update-baseline/ci/all), `openapi-governance.md`, `.github/workflows/openapi-governance.yml`을 생성한다. 기본 CLI는 모노레포 경로가 아닌 config의 `tooling.oaGenCommand`을 사용하고, optional `tooling.setupCommand`은 생성된 CI에서 그 명령을 준비하는 reviewed shell step이다.

`oa-gen collect --spec <raw.yaml> --normalized <normalized.yaml> --upgraded <upgraded.yaml> [--report <collect-report.json>] [--raw <raw-copy.yaml>] [--profile generic|nestjs-swagger|fastapi]`은 raw 보존, stable governance용 normalized artifact, OpenAPI 3.2 분석용 upgraded artifact, collect report를 한 번에 생성한다. `oa-gen normalize`와 `oa-gen upgrade`는 같은 변환을 단일 단계로 노출한다. nullable 변환은 `paths`/`webhooks`/`components.{schemas,responses,parameters,requestBodies,headers,callbacks,pathItems}` 전체를 재귀해 inline schema도 빠뜨리지 않는다.

v1 config는 live parser가 제공되지 않는 deliberate migration boundary다. v1 서비스는 `--force`로 v2 scaffold를 다시 만들고 `tooling.oaGenCommand`/optional `tooling.setupCommand`을 명시한다. 이 migration은 committed baseline을 복사하거나 승인하지 않는다.

스크립트는 `consumers.{governance,review,typegen,inventory,validate,driftManaged}` 매핑을 scaffold time에 셸 변수명으로 해소해 각 케이스 분기에 baked한다. 첫 실행 baseline 부재는 `update-baseline` 힌트와 함께 friendly exit 1로 처리하고, `OA_GEN` 환경변수는 `read -ra`로 split해 glob 확장을 피한다. `--runtime-openapi-url`은 scaffold time에 `URL` 파서로 검증하고 http(s) 외 protocol은 거절한다. `drift` 케이스는 `shift`로 case keyword를 떼고 나머지 인자를 그대로 `oa-gen drift`에 forwarding하므로 `--runtime-header`/`--behavior-log` 등을 그대로 사용할 수 있다. 렌더링된 스크립트 헤더의 `# config fingerprint: <16-char sha256>` 한 줄은 profile/source/artifacts/consumers 정렬 직렬화 해시이며 `fingerprintGovernanceConfig()` public helper로 외부 도구가 재계산 가능하다.

레퍼런스 구현은 `apps/nestjs-ref/`(NestJS Swagger, `--profile nestjs-swagger`)와 `apps/fastapi-ref/`(FastAPI, `--profile fastapi`)이며, 운영 가이드는 [docs/guides/use-cases/nestjs-swagger-governance.md](../guides/use-cases/nestjs-swagger-governance.md), 서비스 템플릿은 [docs/guides/openapi-governance-service-template.md](../guides/openapi-governance-service-template.md)에 있다. 구현은 `packages/codegen/src/cli/lib/openapi-collect.ts`와 `packages/codegen/src/cli/lib/openapi-governance-scaffold.ts`가 맡고, CLI manifest는 `packages/codegen/src/cli/spec/oa-gen-governance.ts`/`docs/cli-spec/oa-gen.governance.json`이 함께 소유한다. 대표 검증은 `packages/codegen/src/__tests__/openapi-collect.test.ts`, `openapi-governance-scaffold.test.ts`, `cli-openapi-collect.test.ts`이다.

### OpenAPI Definition Builder rollback/reference implementation

OpenAPI 문서는 production authoring source가 아니라 build artifact로 다룬다. 현재 production
authoring source는 TypeSpec이며, Definition Builder는 OpenAPI fragment 기반 rollback/reference
implementation으로 유지한다.
개별 schema/path/operation/parameter/response/server fragment는 canonical identity를 갖고, 출력 OpenAPI component name은 target별 naming policy가 결정한다.

#### Canonical ID grammar (US-001)

Canonical ID는 `@oa-sdk/parser`의 `parseDefinitionId()` / `validateDefinitionId()`가 검증하는 source identity다. 문법은 `kind:scope/domain/name`이며 `/`로 구분되는 path segment는 반드시 `scope`, `domain`, `name` 3개여야 한다. `schema:book/Note`, `schema:Note`, `schema:public/book/chapter/Note`는 invalid다.

- `kind`: `schema`, `response`, `parameter`, `requestBody`, `header`, `link`, `callback`, `path`, `operation`, `server`, `tag`, `securityScheme`
- `scope`: `shared`, `public`, `admin`, `internal`, `partner` 같은 API exposure/server family. lower-case segment로 제한한다.
- `domain`: `common`, `book`, `notebook`, `auth`, `user`, `health` 같은 bounded context. lower-case segment로 제한한다.
- `name`: domain-local definition name. component-like kind(`schema`, `response`, `parameter`, `requestBody`, `header`, `link`, `callback`, `securityScheme`)는 PascalCase를 요구한다.

Valid fixture IDs: `schema:public/book/Note`, `schema:public/notebook/Note`, `schema:shared/common/Error`, plus path-flattening guard fixtures `schema:public/a/Name`, `schema:public/aname/Name`, `schema:public/a-name/Name`, and `schema:admin/a/Name`. Duplicate canonical ID는 `validateDefinitionIds()`에서 error로 보고하며, output component name은 후속 naming policy가 target별로 파생한다.

#### Definition node model (US-002)

`DefinitionNode`는 `@oa-sdk/parser`의 public primitive로, fragment source를 registry에 올리기 전 canonical identity와 diagnostics용 source metadata를 함께 운반한다. `createDefinitionNode()`는 canonical id를 `DefinitionId`로 파싱해 `kind`, `scope`, `domain`, `localName`을 채우고, `sourcePath`, `sourcePointer`, `contentHash`, `content`, optional `metadata`, `refs`를 그대로 보존한다.

`DefinitionRef`는 fragment content 안에서 발견한 source ref를 나타낸다. `createDefinitionRef()`는 raw `ref`, `sourcePath`, `sourcePointer`를 보존하고, target canonical id가 이미 알려진 경우 `targetId`로 저장한다. `metadata`는 target server, tags, feature flag, ownership 같은 classification 정보를 위한 optional field이며 canonical id 계층(`kind:scope/domain/name`)에는 포함하지 않는다. 구조가 같은 다른 canonical id를 의도적으로 같은 의미로 취급해야 할 때만 `metadata.semanticAliasOf`에 canonical id 또는 `oa://...` ref를 선언한다. Output `$ref` rewrite는 후속 builder 단계가 담당한다.

#### Definition registry graph (US-003)

`createDefinitionRegistry()`는 `DefinitionNode` 목록을 registry graph로 등록한다. `nodes`와 `nodeById`는 첫 번째 unique canonical id만 보존하고, 같은 canonical id가 다시 들어오면 `definition-registry/duplicate-id` error diagnostic을 만든다. Duplicate diagnostic은 중복 node의 `sourcePath`/`sourcePointer`와 최초 등록 node의 `firstSourcePath`/`firstSourcePointer`를 함께 담고, `lookupSourceLocation`이 제공되면 양쪽 line/column도 보강한다.

Registry ref collection은 `collectDefinitionRefs()`가 담당한다. Fragment `content`를 `#/content/properties/error~1detail/$ref`처럼 JSON Pointer escaping 규칙을 지키며 순회해 `$ref` 문자열을 `DefinitionRef`로 수집하고, registry는 이를 `DefinitionRegistryRefEdge`로 변환한다.

같은 schema `contentHash`가 서로 다른 canonical id에서 발견되면 registry는 기본 `info` severity의 `definition-registry/structural-duplicate` diagnostic을 만든다. 이 diagnostic은 builder를 실패시키지 않으며 `nodes`와 `nodeById`는 계속 canonical id별로 분리된다. `structuralDuplicateSeverity` 옵션으로 `warning` 또는 `off`를 선택할 수 있지만, 기본 정책은 구조 유사성을 의미 동치로 승격하지 않는 것이다. `metadata.semanticAliasOf`가 등록된 target을 가리키면 registry는 `semanticAliases`에 source/target/content hash metadata를 기록하고 해당 pair를 intentional alias로 취급한다.

#### Source ref resolution (US-004)

Canonical source ref syntax는 `oa://{kind}/{scope}/{domain}/{name}`이며, registry는 `oa://schema/shared/common/Error`를 canonical id `schema:shared/common/Error`로 정규화해 edge/ref의 `targetId`에 보존한다. 상대 file ref는 registered definition source와 일치할 때 canonical id로 정규화한다. 예를 들어 `/workspace/fragments/schema/public/book/Note.yaml#/content` 안의 `./Author.yaml#/content`는 같은 디렉터리의 `Author.yaml`에 등록된 node가 있으면 `schema:public/book/Author`로 해소된다. Pointer가 없는 상대 file ref는 해당 파일에 등록된 definition node가 하나일 때만 해소하고, 같은 파일에 여러 node가 있으면 explicit JSON Pointer가 필요하다.

Registry는 duplicate id 외에도 source ref diagnostic을 만든다. 유효한 canonical ref 또는 file ref가 등록된 target을 찾지 못하면 `definition-registry/missing-ref`, `oa://...` 문법이 canonical id로 정규화되지 않거나 legacy/internal/absolute ref처럼 builder source ref로 지원하지 않는 형식이면 `definition-registry/unsupported-ref`를 보고한다. Ref diagnostic은 raw `ref`, source path/pointer, optional line/column, file target path/pointer 또는 target canonical id를 보존한다. Output `$ref` rewrite는 다음 builder 단계의 책임이다.

#### Output `$ref` rewrite (US-005)

`rewriteDefinitionOutputRefs()`는 registry의 resolved `targetId`와 node source pointer를 사용해 fragment `content`와 `refs` 안의 source `$ref`를 표준 OpenAPI component `$ref`로 변환한다. 기본 output name은 target node의 `localName`이며, target-local naming policy가 준비되면 `outputNames` map 또는 `resolveOutputName` callback으로 `schema:public/notebook/Note -> NotebookNote` 같은 alias를 주입한다.

Component-like kind의 output 위치는 고정 매핑이다: `schema -> #/components/schemas`, `response -> #/components/responses`, `parameter -> #/components/parameters`, `requestBody -> #/components/requestBodies`, `header -> #/components/headers`, `link -> #/components/links`, `callback -> #/components/callbacks`, `securityScheme -> #/components/securitySchemes`. 출력명 segment는 JSON Pointer escaping을 적용한다. Missing/unsupported source ref는 registry diagnostic을 그대로 보존하고 rewrite하지 않으므로 build emit 단계는 `valid` registry만 OpenAPI 문서로 내보내야 한다.

#### Target-local output naming (US-006)

`allocateDefinitionOutputNames()`는 target bundle에 포함된 `DefinitionRegistryNode` 목록만 입력으로 받아 output component name을 할당한다. Allocation은 전역 cache나 canonical id별 singleton을 사용하지 않으므로 같은 canonical id가 public/admin/internal target에 동시에 포함되어도 각 target은 독립적으로 `outputNames` map을 갖는다. Canonical ID는 변경하지 않고, build emit/rewrite 단계는 allocation 결과를 `rewriteDefinitionOutputRefs({ outputNames })`에 주입한다.

정책 순서는 target-local이다. Explicit alias map에 canonical id가 있으면 그 이름을 우선 사용하고 alias metadata reason은 `explicit-alias`가 된다. Alias가 없는 component-like definition은 같은 kind 안에서 local name이 unique하면 `localName`을 그대로 보존하고 reason은 `preserve-if-unique`다. Alias가 없는 동일 kind/local name이 target 안에서 둘 이상이면 domain prefix를 붙여 `schema:public/book/Note -> BookNote`, `schema:public/notebook/Note -> NotebookNote`처럼 만들고 reason은 `domain-prefix`다. Explicit alias로 충돌이 해소된 나머지 node는 다시 preserve-if-unique 대상이 될 수 있다.

Allocation 결과는 `outputNames: Map<CanonicalDefinitionId, string>`, `aliases: DefinitionOutputAliasMetadata[]`, `aliasById: Map<CanonicalDefinitionId, DefinitionOutputAliasMetadata>`를 함께 낸다. Alias metadata는 canonical id, kind, scope, domain, localName, outputName, policy reason을 보존해 build report나 downstream generator가 source identity와 output component name을 추적할 수 있게 한다. 최종 output name이 같은 component section 안에서 둘 이상의 canonical id에 매핑되면 자동 병합하지 않고 `definition-output-name/collision` error diagnostic을 만든다.

#### Server/domain collision simulation (US-007)

`allocateDefinitionOutputNames(nodes, { targetName })`는 naming 결과와 final collision을 기계가 읽을 수 있는 `collisionReport` 배열로도 반환한다. Report row는 target server scope에서 output component name이 왜 보존/변경/실패했는지 추적하기 위한 stable shape이다.

```ts
{
  canonicalId: 'schema:public/book/Note',
  targetName: 'public-api',
  kind: 'schema',
  scope: 'public',
  domain: 'book',
  localName: 'Note',
  outputName: 'BookNote',
  reason: 'domain-prefix',
  severity: 'warning',
}
```

Report severity는 `preserve-if-unique`면 `info`, domain prefix rename이면 `warning`, explicit alias rename이면 `warning`, 최종 output name collision이면 `error`다. Error row는 `reason: 'output-name-collision'`을 사용하고, 세부 colliding canonical id 목록은 기존 `definition-output-name/collision` diagnostic의 `ids`에서 확인한다.

Fixture target은 `packages/schemas/src/targets/public-api.yaml`과 `packages/schemas/src/targets/admin-api.yaml`에 둔다. `public-api`는 `schema:public/book/Note`와 `schema:public/notebook/Note`를 함께 포함해 `BookNote`/`NotebookNote` rename을 검증하고, flattening guard fixture인 `schema:public/a/Name`, `schema:public/aname/Name`, `schema:public/a-name/Name`도 포함한다. `admin-api`는 `schema:admin/book/Note`, `schema:admin/notebook/Note`, `schema:admin/a/Name`을 포함해 같은 local name이 target-local report 안에서 독립적으로 처리됨을 검증한다. 두 target 모두 `schema:shared/common/Error`를 포함할 수 있지만 각 target allocation은 별도 `outputNames`/`collisionReport`를 갖는다.

#### Flattening guard simulation (US-008)

Canonical ID와 output symbol은 서로 다른 축이다. `schema:public/a/Name`, `schema:public/aname/Name`, `schema:public/a-name/Name`, `schema:admin/a/Name`은 모두 distinct canonical identity로 registry에 등록되어야 하며, string flattening 결과가 같아 보인다는 이유로 같은 definition으로 dedupe하면 안 된다.

Flattening risk test는 target-local allocator에 explicit alias map을 넣어 naive flattened naming policy가 세 public fixture를 모두 `AName`으로 내보내려는 상황을 시뮬레이션한다. 이 경우 allocator는 canonical-id keyed `outputNames` map과 alias metadata를 유지하되 `valid: false`를 반환하고, `definition-output-name/collision` diagnostic에 attempted output name `AName`과 colliding canonical IDs 전체를 담는다. `collisionReport` row들은 `reason: 'output-name-collision'`, `severity: 'error'`가 되며, default fail-on-collision policy에서는 자동 semantic merge나 late rename 없이 build가 실패해야 한다.

#### Duplicate and dedupe policy (US-009)

Duplicate policy는 source identity, output symbol, structural hash를 분리한다. Duplicate canonical id는 항상 error이며 registry는 첫 번째 node만 보존하고 중복 source location을 diagnostic에 담는다. Duplicate output name은 target-local naming policy가 `preserve-if-unique`, `domain-prefix`, explicit alias 순서로 해결하고, 그래도 같은 component section/output name에 여러 canonical id가 남으면 `definition-output-name/collision` error로 실패한다.

동일 schema hash는 자동 dedupe 조건이 아니다. 서로 다른 canonical id가 같은 `contentHash`를 공유하면 registry는 기본 `info` diagnostic으로만 보고하고 두 definition을 그대로 유지한다. Downstream builder가 structural dedupe를 허용하려면 source fragment가 `metadata.semanticAliasOf: 'schema:...'` 또는 `metadata.semanticAliasOf: 'oa://...'`를 명시해야 하며, 이 경우 registry `semanticAliases`가 유일한 opt-in dedupe signal이다. Alias target이 없거나 문법이 invalid면 일반 ref diagnostic처럼 error가 된다.

#### Target bundle config and selection (US-010)

Target config는 OpenAPI emit 전 단계에서 registry node 집합을 고르는 선언이다. `selectDefinitionTarget(registry, config)`는 직접 매칭된 path node에서 시작해 registry `refEdges`를 따라 schema, parameter, response, requestBody, header, link, callback, securityScheme 등 referenced component를 재귀 포함한다. OpenAPI document emit은 이 selected target result를 그대로 소비한다.

```yaml
name: public-api
scopes:
  - shared
  - public
domains:
  - common
  - book
  - notebook
servers:
  - url: https://api.example.test
includePaths:
  - /books/{bookId}/notes
namingPolicy:
  aliases:
    schema:public/book/Note: PublicBookNote
```

Format:
- `name`: target-local report와 output name allocation에 쓰는 stable target id.
- `scopes`: target이 포함할 canonical scope 목록. Public target은 보통 `shared` + `public`, admin target은 `shared` + `admin`, internal target은 `shared` + `internal`을 선언한다.
- `domains`: target이 포함할 bounded-context 목록. Shared component를 쓰려면 `common` 같은 shared domain도 포함해야 한다.
- `servers`: emitted OpenAPI document의 `servers`가 될 OAS Server Object 배열.
- `includePaths`: exact OpenAPI path 문자열 목록. Path definition node는 `metadata.path` 또는 `metadata.openApiPath`로 matching path를 선언한다.
- `namingPolicy.aliases`: optional target-local canonical id -> output component name override. Alias가 없으면 US-006의 preserve-if-unique/domain-prefix/collision policy가 적용된다.

Selection은 configured scope/domain 밖의 transitive ref를 자동 포함하지 않고 `definition-target/disallowed-ref` error diagnostic으로 보고한다. `includePaths`가 configured scope/domain 안의 path node와 매칭되지 않으면 `definition-target/path-not-found` error diagnostic이 된다. Selection 결과는 `directPathIds`, selected `nodes`/`nodeById`, selected-source `refEdges`, 그리고 `outputNameAllocation`을 함께 반환하므로 후속 emit 단계가 같은 target-local output name map을 그대로 사용할 수 있다.

#### OpenAPI document emit (US-011)

`emitDefinitionOpenApiDocument(selection, options)`는 `selectDefinitionTarget()` 결과를 OpenAPI 3.2 document artifact로 materialize한다. Root object는 `openapi`(기본 `3.2.0`), `info`(옵션 또는 target name 기반 기본값), target `servers`, selected `paths`, `webhooks`(없어도 `{}`), `components`를 항상 포함한다.

Emit은 selected target의 `outputNameAllocation.outputNames`를 `rewriteDefinitionOutputRefs()`에 주입한 뒤, path definition node는 `metadata.path`/`metadata.openApiPath` 값으로 `paths`에 배치하고 component-like node는 kind별 components section에 배치한다. Emitted document 안의 `$ref`는 local OpenAPI `$ref`만 허용하며, source `oa://...` 또는 non-local ref가 남으면 `definition-openapi-emit/unrewritten-ref` error diagnostic으로 실패한다.

OAS 3.2 content fields는 필터링하지 않고 fragment content를 보존한다. Media Type Object의 `itemSchema`, Example Object의 `dataValue`/`serializedValue` 같은 3.2 전용 필드는 ref rewrite 외에는 그대로 output에 남는다. Emit 결과는 내부에서 `validateDocument()`를 실행해 validation errors를 `definition-openapi-emit/validation-error` diagnostic으로 연결하고, valid output은 `validateDocument()`를 통과해야 한다.

Renamed definitions는 output document root extension `x-oa-sdk-definition-aliases`에 alias metadata로 포함한다. Result sidecar report도 `aliases`, `renamedAliases`, `collisionReport`, `rewrites`를 제공해 source canonical id와 target-local output name을 추적할 수 있다.

Fixture target `packages/schemas/src/targets/book-notebook-api.yaml`은 `/books/{bookId}/notes`와 `/notebooks/{notebookId}/notes`를 함께 include해 `schema:public/book/Note`와 `schema:public/notebook/Note` source-name collision이 emitted components에서 `BookNote`/`NotebookNote`로 분리되는 것을 검증한다. Production `.merged.yaml`은 이 story에서 교체하지 않고 TypeSpec pipeline과 병렬인 rollback/reference artifact로 둔다.

#### Definition builder CLI (US-012)

`oa-gen build-spec`는 target config와 definition fragments를 읽어 selected target OpenAPI 3.2 artifact를 생성한다. CLI는 `@oa-sdk/codegen`에 위치하며 parser의 public builder primitives를 조합한다. 기본 fragment directory는 target file sibling 기준 `../fragments`이고, 필요하면 `--fragments`로 override한다.

```bash
oa-gen build-spec \
  --target packages/schemas/src/targets/book-notebook-api.yaml \
  --output artifacts/book-notebook-api.yaml \
  --diagnostics artifacts/book-notebook-api.diagnostics.json \
  --collision-report artifacts/book-notebook-api.collisions.json \
  --composition-report artifacts/book-notebook-api.composition.json \
  --provenance artifacts/book-notebook-api.provenance.json \
  --metadata-registry artifacts/book-notebook-api.metadata.json \
  --behavior-log artifacts/book-notebook-api.behavior.jsonl \
  --behavior-db artifacts/book-notebook-api.behavior.sqlite
```

Options:
- `--target, -t`: target config YAML/JSON path. `name`, optional root `info`, `scopes`, `domains`, `servers`, optional `tags`, `includePaths`, optional `includeDefinitions`, optional `namingPolicy.aliases`를 사용한다.
- `--fragments`: definition fragments root. 생략하면 target config의 sibling `../fragments`를 사용한다.
- `--output, -o`: valid build일 때 쓸 OpenAPI YAML artifact path. 생략하면 YAML을 stdout으로 출력한다.
- `--diagnostics`: registry/target/output-name/emit diagnostics를 담은 JSON sidecar path. 실패해도 기록한다.
- `--collision-report`: target-local naming collision report JSON path. `canonicalId`, `targetName`, `kind`, `scope`, `domain`, `localName`, `outputName`, `reason`, `severity` row array를 기록한다.
- `--composition-report`: target composition report JSON path. Registry/selection/emit report 데이터에서 direct path ids, direct retained definition ids, transitive component ids, omitted node counts by scope/domain/kind, output path/component canonical id links, output aliases, collision report, source refs를 기록한다. 출력 OpenAPI를 재파싱하지 않는다.
- `--provenance`: output pointer provenance map JSON path. `#/paths/{path}`, `#/paths/{path}/{method}`, `#/components/{section}/{name}` pointer별 `canonicalId`, `kind`, `sourcePath`, `sourcePointer`, `contentHash`를 기록한다. Provenance는 artifact content를 대체하지 않는 sidecar이며 stable pointer ordering으로 기록한다.
- `--metadata-registry`: internal metadata registry JSON path. `#/paths/{path}`, `#/paths/{path}/{method}`, `#/components/{section}/{name}` pointer별 fragment `metadata`, logical `identityKey`, opaque `stableKey`, explicit/generated `trackingId`, source refs, inline example source pointers를 기록한다. Tracking id는 `metadata.trackingId`, `metadata.tracking`, `metadata.tracking.id`, 또는 path fragment `metadata.operations.{method}`에서 명시할 수 있고, 없으면 `stableKey` seed로 stable 생성한다. 명시 tracking id는 trim 후 `^trk_[a-z0-9][a-z0-9_:-]*$`를 만족해야 하며 invalid 값은 `metadata-registry/invalid-tracking-id` error로 보고한다. `identityKey`는 definition entry의 `definition:{canonicalId}` 또는 operation entry의 `operation:{pathCanonicalId}:{method}`이고, `stableKey`는 이를 versioned SHA-256 seed로 해시한 `oa-meta:v1:{digest}` 형식이다. 따라서 schema/path/example content hash 변경, OpenAPI path 문자열 변경, source file 이동, output alias/component name 변경에 영향받지 않는다. canonical id rename은 fragment `metadata.replaces`에 이전 canonical id를 문자열 또는 문자열 배열로 선언해 같은 `identityKey`/`stableKey`를 이어받는다. Invalid replacement id는 `metadata-registry/invalid-replaces-id` error로 보고한다. 같은 sidecar 안에서 output pointer, `trackingId`, 또는 `stableKey`가 중복되면 `metadata-registry/duplicate-output-pointer`, `metadata-registry/duplicate-tracking-id`, `metadata-registry/duplicate-stable-key` error diagnostic으로 build를 실패시킨다. 실패한 build에서도 metadata sidecar는 `duplicates.outputPointers`, `duplicates.trackingIds`, `duplicates.stableKeys`를 보존한다.
- `--behavior-log`: append-only behavior JSONL path. command completion 시 `build_openapi_target` behavior entity를 1건 기록하고, `actor`/`target`/`input`/`context`/`result`/`audit`/`metrics` component payload를 함께 남긴다.
- `--behavior-db`: append-only behavior SQLite DB path. `behavior_records` table에 behavior entity 1건을 insert하고, `record_json` column에 full payload를 보존한다.

Metadata registry versioning:
- `schemaVersion: oa-gen.metadata-registry.v1`은 sidecar JSON envelope/schema version이다. Backward-compatible 필드 추가는 `v1`을 유지하고, 필드 제거/rename/의미 변경이나 `entries`/`duplicates` 구조 breaking change는 `v2`로 승격한다.
- `stableKey: oa-meta:v1:{digest}`의 `oa-meta`는 metadata stable key namespace이고, `v1`은 stable key 생성 알고리즘 버전이다. `schemaVersion`과 독립적으로 관리한다.
- Stable key algorithm `v1`은 `identityKey`를 `oa-gen.metadata-registry.stable-key.v1` domain seed로 SHA-256 해시하고 앞 32 hex를 사용한다. Generated tracking id는 `stableKey`를 `oa-gen.metadata-registry.tracking-id.v1` domain seed로 SHA-256 해시하고 앞 16 hex를 `trk_` 뒤에 붙인다.
- `identityKey` 문법, hash domain, digest 길이, namespace, generated tracking id 알고리즘을 바꾸면 `oa-meta:v2`가 필요하다. 그 경우 reader는 `v1`과 `v2`를 모두 읽고, entry에 `previousStableKeys` 또는 별도 migration sidecar로 `v1 -> v2` 매핑을 남겨야 한다.

CLI build는 fragment `content` 기준 SHA-256 hash를 생성해 registry에 넘기고 YAML source location index를 연결해 duplicate/ref diagnostics에 source coordinates를 보강한다. Duplicate canonical id, missing/unsupported source ref, target disallowed ref, output name collision, unrewritten ref, emitted document validation error 중 하나라도 `error` severity이면 artifact output은 쓰지 않고 exit code 1로 종료한다. Diagnostics/collision/composition/provenance/metadata sidecar는 실패한 CI run에서도 분석할 수 있도록 output artifact와 독립적으로 작성한다.

`oa-gen review`는 `--base-provenance`와 `--head-provenance`를 받으면 provenance map을 pointer별로 비교해 added/removed/changed provenance entries를 JSON report와 Markdown `Provenance Changes` 섹션에 포함한다. `--base-metadata-registry`와 `--head-metadata-registry`를 받으면 metadata registry entry도 pointer별로 비교해 JSON report와 Markdown `Metadata Registry Changes` 섹션에 포함한다. 두 diff는 artifact freshness나 breaking diff를 대체하지 않고, API content diff가 깨끗하더라도 source ownership/content hash 변경이나 stable key/tracking id drift를 review evidence로 드러낸다.

Builder WorkspaceIndex metadata는 SQLite schema를 늘리지 않고 기존 row를 재사용한다. Target config 파일과 fragment 파일은 `files`에 content hash/mtime/realpath로 저장하고, fragment id는 `components.section = definition-fragment`, target bundle은 `components.section = definition-target`으로 기록한다. Fragment source `$ref`는 fragment file → target fragment file `refs` edge가 되고, target config는 direct path root fragment와 explicit retained `includeDefinitions` fragment로 향하는 `refs` edge를 기록한다. 기존 `refs.to_file` 역방향 dirty propagation이 schema fragment 변경을 참조 fragment와 target config까지 전파하므로 target bundle은 직접 또는 transitively 포함한 fragment가 바뀔 때 dirty가 된다. Target config 파일 자체가 바뀌면 reverse dependency가 없으므로 해당 target만 dirty가 되며, no-op/SQLite fallback은 ADR-006 원칙대로 scanned target을 full rebuild 대상으로 취급한다.

#### TypeSpec as Canonical Schema Pipeline

Schema composition is now TypeSpec-first. `packages/schemas/src/.merged.yaml` is generated from the `packages/schemas/typespec/main.tsp` entrypoint and its domain modules, including `world-model.tsp`, through the `oa-sdk.typespec-bundle.v1` manifest, OA SDK TypeSpec extension restore, approved snapshot drift gates, and OpenAPI 3.2 validation. The OpenAPI/Definition Builder path remains available as an explicit rollback/reference path through `:openapi` commands; the legacy whole-domain merge script has been removed, and `src/domains/**/spec.yaml` files are archived historical/migration reference material.

Current TypeSpec status: the TypeSpec-restored production artifact has 34 operations, including 7 World Model operations from `world-model.tsp`, and 49 schemas; it restores 195 OA SDK extension-derived semantic entries and keeps 0 reviewed restored-vs-reference differences in `accepted-restored-drift.json`. The contract version is `0.5.0`, owned by `packages/schemas/typespec/version.tsp` and emitted through TypeSpec `@info` to OpenAPI `info.version`. `pnpm schema:validate` is the canonical gate: it builds parser/codegen, emits `.merged.yaml` through `schema:typespec-check`, downgrades to 3.1, runs Spectral/Redocly, and then runs strict `oa-gen validate --require-32`.

The authoring workflow is defined in [`docs/guides/typespec-authoring-conventions.md`](../guides/typespec-authoring-conventions.md), the current promotion/recovery procedure is in [`docs/internal/typespec-roundtrip/production-operations.md`](typespec-roundtrip/production-operations.md), and the extension-vocabulary migration notes are in [`docs/internal/architecture/009-typespec-first-authoring.md`](architecture/009-typespec-first-authoring.md).

| 단계 | Production TypeSpec path |
|------|-------------------------|
| Source layout | `packages/schemas/typespec/main.tsp` composition entrypoint + `metadata/{service,security,common-components}.tsp` + `version.tsp` + `common/auth/health/me/users/world-model.tsp` domain modules + `oa-sdk.typespec-bundle.json` |

Production schema requirements now become ongoing governance requirements:

- `.merged.yaml` must be generated by the TypeSpec production bundle for default validation/build/bundle commands.
- `pnpm schema:rollback-check` must keep the OpenAPI/Definition Builder fallback green.
- TypeSpec-restored drift must either match the accepted hash-pinned manifest or be burned down intentionally.
- Candidate metadata must bind the candidate to its manifest, bundle-source hash, approved-snapshot hash, and candidate hash. A promotion must fail if the source bundle or approved snapshot changed while it was being reviewed.
- A nonempty `accepted-restored-drift.json` blocks snapshot promotion. Its reset is an explicit paired action: `pnpm schema:approve-typespec-reference -- --write --clear-accepted-restored-drift`, reviewed with the snapshot change.
- A paired snapshot-and-drift promotion must first persist a local recovery journal. The next approval or TypeSpec gate completes only its hash-recognized before/after state and rejects unrelated manual edits rather than overwriting them.
- A TypeSpec bundle must never select another bundle's approved snapshot implicitly; `expectedOpenapi` in that bundle's manifest is the sole promotion target.
- Contract versioning follows SemVer: breaking consumer changes bump major (or `0.MINOR` before 1.0), backward-compatible additions bump minor, and compatible corrections bump patch. Snapshot, bundle, extension, and candidate schema versions are separate version channels.
- `.merged.3.1.yaml` must continue to be derived from the active 3.2 artifact through `downgrade-3.1.ts` with the same sidecar contract.
- `pnpm schema:validate`, `pnpm --filter @oa-sdk/schemas test`, and downstream codegen/router/client/mock-server tests are the regression surface for future changes.
- Rollback now means using the explicit `:openapi` commands while repairing TypeSpec output, or reverting the source-path switch if TypeSpec output cannot preserve validation/downstream behavior.

| 개념 | 계획 |
|------|------|
| Canonical identity | `kind:scope/domain/name` 고정 계층. 예: `schema:public/book/Note`, `schema:public/notebook/Note`, `schema:shared/common/Error`. source identity와 output component name을 분리 |
| Definition registry | fragment를 unique node로 등록하고 JSON Pointer-aware `$ref` edge, content hash, source path/pointer, duplicate id diagnostics를 수집 |
| Source refs | `oa://schema/public/book/Note` 같은 canonical ref와 상대 file ref를 canonical id로 정규화 |
| Output refs | registry `targetId`를 build target의 output name과 kind별 component 위치로 변환해 `#/components/schemas/{OutputName}` 같은 표준 OpenAPI ref로 rewrite |
| Naming policy | target-local `allocateDefinitionOutputNames()`가 explicit alias, `preserve-if-unique`, `domain-prefix`를 적용. `book.Note`와 `notebook.Note`는 source name을 바꾸지 않고 `BookNote`/`NotebookNote`처럼 출력명만 분리 |
| Namespace scope | 이름 충돌 해결은 target server의 포함 node 집합 안에서 kind → domain → local name 순서로 처리. 같은 local name이라도 target bundle마다 포함 집합이 다르므로 output name allocation은 target-local임 |
| Flattening guard | `schema:public/a/Name`, `schema:public/aname/Name`, `schema:public/a-name/Name`, `schema:admin/a/Name`은 flatten 결과가 같을 수 있어도 다른 canonical identity다. builder는 string flattening만으로 동치 추론을 하지 않고 attempted output name과 모든 colliding canonical IDs를 `output-name-collision`으로 보고 |
| Collision simulation | public/admin target fixture에서 server target → domain → local name 순서의 rename과 target-local report를 검증. flattening output collision은 fail-on-collision diagnostic으로 검증되며, book-notebook target fixture emit은 `BookNote`/`NotebookNote` output을 검증 |
| Dedupe policy | duplicate canonical id는 error. 동일 schema hash는 기본 info diagnostic only. 의미가 다른 정의는 자동 structural dedupe 금지. opt-in semantic dedupe는 `metadata.semanticAliasOf`와 registry `semanticAliases`로만 표현 |
| Target bundle | `name`, optional root `info`, `scopes`, `domains`, `servers`, optional `tags`, `includePaths`, optional `includeDefinitions`, `namingPolicy.aliases` format으로 선언. `selectDefinitionTarget()`가 exact path match + explicit retained definitions + transitive ref walk + target-local output name allocation을 수행하고 OpenAPI emit에 넘긴다 |
| OpenAPI emit | `emitDefinitionOpenApiDocument()`가 selected target을 OAS 3.2 document로 materialize하고 rewritten local `$ref`만 허용. Alias metadata는 root extension 또는 result sidecar report로 제공 |
| Definition builder CLI | `oa-gen build-spec --target ... --output ... --diagnostics ... --collision-report ... --composition-report ... --provenance ... --metadata-registry ...`가 target OpenAPI artifact와 machine-readable sidecar를 생성. Duplicate canonical id 또는 unresolved source ref는 non-zero exit |
| Builder WorkspaceIndex metadata | fragment file/hash/id/ref metadata와 target config → direct path root edge를 기존 `WorkspaceIndex` row로 저장. 변경 감지는 full rebuild correctness를 유지하면서 affected target 계산에만 사용 |
| Migration | `packages/schemas/scripts/merge.ts`는 제거됨. Production `.merged.yaml`은 TypeSpec bundle에서 생성되고, rollback `.merged.yaml`은 target config + fragments에서 `oa-gen build-spec`로 생성 |

패키지 책임: `@oa-sdk/schemas`는 fragment layout/target config/fixtures/migration을 소유하고, `@oa-sdk/parser`는 validation/source/ref graph primitive를 제공하며, `@oa-sdk/codegen`은 `oa-gen build-spec` CLI와 WorkspaceIndex 연동을 소유한다.
