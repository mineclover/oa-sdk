# @oa-sdk/webmcp-peer

## 0.2.0

### Minor Changes

- 181979c: `PeerMcpSession` keeps to the relay's limit of requests in flight per agent WebSocket, now exported as `PEER_RELAY_MAX_PENDING_REQUESTS` (64) from `./config` and the package root and used by the relay too. Over a relay socket (any transport that is not `raw`; the Streamable HTTP one is), a request past 64 unanswered ones waits, in order, and is sent once an earlier one has been answered, instead of failing with the relay's `TOO_MANY_PENDING_REQUESTS` (-32087). A request holds its place until the relay answers it, even after its caller stopped waiting at a shorter timeout, since the relay counts it until then. The wait counts toward the request's timeout (`REQUEST_TIMEOUT`, never sent), and `disconnect()` or a closed transport ends waiting requests like pending ones. An id over 1 KiB of JSON, which the relay answers without the id, is refused before it is sent with `PeerMcpError` `REQUEST_ID_TOO_LARGE` (`details: { bytes, limitBytes }`) instead of waiting for its timeout.

  The live demo's provider (`examples/live-demo/host-provider.js`) numbers its `register` frames with `registerSeq` as the SDK provider does, and matches the relay's `CATALOG_INVALID` / `CATALOG_TOO_LARGE` refusals to the latest frame by that number.

- 6c959bc: The relay's Streamable HTTP endpoint (`/p/:id/mcp`) now follows the initialize-era MCP transport rules (2025-11-25), which is what stock MCP hosts speak. MCP 2026-07-28 removed `initialize`; the official SDK 1.x supports up to 2025-11-25, and SDK 2.x opens with `initialize` (or, in `auto` mode, probes `server/discover` first and falls back to it). Several replies change, so review the items marked **behavior change**.

  - **Behavior change:** `initialize` negotiates within the new `MCP_INITIALIZE_PROTOCOL_VERSIONS` (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`). A request for `2026-07-28`, an unknown version, or no version now gets `2025-11-25` instead of `2026-07-28`, which the official SDK rejected as unknown. `server/discover` on this endpoint reports the same negotiated version. `PROTOCOL_VERSION` (`./client`), which `PeerMcpSession` sends in `initialize`, is now `2025-11-25`. `MCP_PROTOCOL_VERSION` and `MCP_PROTOCOL_VERSIONS` keep `2026-07-28` for the provider's own stateless dialect.
  - **Behavior change:** a request other than `initialize` whose `MCP-Protocol-Version` header names an unsupported version gets HTTP 400 with JSON-RPC error `-32600` `UNSUPPORTED_PROTOCOL_VERSION` and `data: { supported, requested }`. A missing header is still accepted. A 2026-07-28 client probing `server/discover` gets this 400 and falls back to `initialize`.
  - **Behavior change:** notifications (no `id`), including `notifications/initialized`, get 202 with an empty body instead of a JSON body.
  - **Behavior change:** a request with `id: null` gets 400 with `-32600` `INVALID_REQUEST`; before, it was forwarded as a notification.
  - **Behavior change:** a body over `PEER_RELAY_MAX_REQUEST_BYTES` (256 KiB - 1 KiB, the relay's request limit on every transport) gets 413 `REQUEST_TOO_LARGE` instead of being truncated at 150,000 bytes and answered `PARSE_ERROR`. The rest of the body is read and discarded (up to 16 times the limit, past which the request is destroyed), so the connection stays usable for the next request.
  - **Behavior change:** `DELETE /p/:id/mcp` gets 405 with `Allow: GET, POST`, because the relay issues no `Mcp-Session-Id`.
  - **Behavior change:** the HTTP `initialize` reply advertises `capabilities.tools.listChanged: false`. This endpoint has no server-to-client stream; catalog changes reach WebSocket clients and surface here as `CATALOG_CHANGED`. The WebSocket provider still advertises `true`.
  - CORS `Access-Control-Allow-Headers` (preflight, JSON responses and 304 replies) now lists `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`, so browser-hosted MCP clients pass the preflight after `initialize`.

- 54a8063: The relay, provider, agent client and config tiers now share one set of protocol constants and parsing rules: the protocol identifiers, how an `Authorization` header is read, the room id grammar, and the tool-catalog contract (relay protocol spec O-14, O-15, O-16, O-32, O-52, O-53, O-54, O-55). Several of them change what a peer sees, so review the items marked **Behavior change**.

  - New exports from `./config` and the package root: `WEBMCP_PROTOCOL` (`webmcp-peer/1`, the `protocol` of frames, `/config` and profiles; `WEBMCP_SUBPROTOCOL` stays `webmcp-peer.v1` for the WebSocket subprotocol, which cannot contain `/`), `WEBMCP_ROOM_ID_PATTERN` (`/^[A-Za-z0-9_-]{1,128}$/`), `PEER_CATALOG_MAX_TOOLS` (128) and `PEER_CATALOG_MAX_TOOL_NAME_LENGTH` (256). The relay, codec, provider and client use these constants instead of their own strings and numbers.
  - **Behavior change:** `discoverPeerCatalog` over `GET /mcp/catalog` returns the relay's `protocol` (`webmcp-peer.v1`) as a new `protocol` field and puts the MCP revision (`PROTOCOL_VERSION`, `2025-11-25`) in `protocolVersion`. Before, `protocolVersion` held `webmcp-peer.v1`.
  - **Behavior change:** every relay route reads `Authorization` the same way: the first value, the `Bearer` scheme in any case, followed by one or more spaces. Approval, session status, revoke, rotate and `POST /p/:id/mcp` now accept `bearer <token>` or `Bearer  <token>`, which they refused with 401 before (only `POST /p` accepted them). `X-Publish-Key` is still read for the publish key only, and only without a Bearer token. The public `WebMcpPeerServer.bearerToken(req)` now returns the Bearer token alone and no longer falls back to `X-Publish-Key`; the publish key is read by the new protected `publishKeyToken(req)`.
  - **Behavior change:** the relay keeps client tokens only as their SHA-256 hex and finds a ticket by the hash of the token presented, like it compares the provider token and the reconnect lease. `RoomEntry.clientTokens` is renamed `clientTickets` (keyed by the token hash), `PendingApprovalRequest.clientToken` is renamed `clientTokenHash`, the protected `findClientToken` is renamed `findClientTicket` (returning `tokenHash`), and `closeClientTicket` takes the token hash.
  - **Behavior change:** every room route and upgrade path takes room ids of the one grammar `^[A-Za-z0-9_-]{1,128}$`. A lifecycle route (reclaim, join, approval, session status, revoke, rotate) answers an unknown id of the grammar, such as one with upper case or `_`, with 404 `ROOM_NOT_FOUND` instead of 404 `NOT_FOUND`, and a hex id over 128 characters now gets `NOT_FOUND` on every route.
  - **Behavior change:** the agent client checks room ids against the grammar. `parseRoomId` returns `undefined` for a value that names no valid id (before, it returned any path segment), and `PeerMcpSession`, `discoverPeerCatalog`, `joinPeerRoom`, `getPeerSessionStatus`, `waitForPeerApproval` and `rotatePeerRoom` refuse such a room id or invitation URL with `ROOM_ID_INVALID` before sending anything. `discoverPeerCatalog` no longer reads an invalid `roomId` as "no room" and lists the deployment catalog instead.
  - **Behavior change:** the provider normalizes its server URL the same way in `connect()` and `refreshRoom()`, case-insensitively (`HTTPS://relay` is no longer turned into `http://HTTPS://relay`), builds its socket URL with a case-insensitive `http` to `ws` replacement, and URL-encodes the room id in every relay URL, as the agent client does.
  - **Behavior change:** the agent client's `normalizeTools` refuses a tool name with leading or trailing whitespace with `INVALID_TOOL_DESCRIPTOR` instead of trimming it, so it accepts exactly the catalogs the relay accepts. The relay's `CATALOG_INVALID` reason now spells out the whole contract: `register.tools must be an array of at most 128 tools, each with a unique, non-empty name of at most 256 UTF-16 code units without leading or trailing whitespace and an inputSchema object of type "object"`.
  - **Behavior change:** `POST /p` and rotate trim a room `alias` and keep at most its first 256 code points, as join does for `clientLabel`. Before, an alias up to the 64 KiB body limit was kept and shown in every room descriptor, the public `GET /p/:id/mcp` included.
  - **Behavior change:** the deployment catalog is looked up relative to the relay's `cwd` option instead of `process.cwd()`, a relative `$WEBMCP_CATALOG_PATH`/`$FRAMEBOOK_MCP_CATALOG_PATH` is resolved against `cwd` too, and the `packages/peer-server/api/webmcp-tools.json` candidate of another package is gone. `loadDeploymentCatalog(injected, cwd?)` takes the directory as a second argument.
  - **Behavior change:** the relay opens a `SqlitePublishRateLimitStore` when its configuration names one: `resolvePeerServerConfig` reads `publishRateLimitSqlitePath` from `--publish-rate-limit-sqlite-path`, the options, the config file and `FRAMEBOOK_PUBLISH_RATE_LIMIT_SQLITE_PATH`/`WEBMCP_PUBLISH_RATE_LIMIT_SQLITE_PATH` (resolved against `cwd`; an empty path throws `PUBLISH_RATE_LIMIT_SQLITE_PATH_INVALID`). An injected `publishRateLimitStore` still wins, and SQLite takes precedence over `publishRateLimitPath`. The relay closes the SQLite store it opened in `close()`. Before, those variables were only read by `createPublishRateLimitStoreFromEnv`, which the relay never called.
  - **Behavior change:** the unused `journalPath` option, `--journal-path` flag, config-file key and `FRAMEBOOK_COLLAB_JOURNAL_PATH` variable are removed from `WebMcpPeerServerOptions`, `PeerServerConfig`, `CliParsedArgs` and `resolvePeerServerConfig`.
  - **Behavior change:** `PeerServerPublicConfig.defaults` declares the `maxRoomTtlMs` that `GET /config` sends, and `fetchPeerServerConfig` rejects a document whose `defaults.maxRoomTtlMs` is not a finite number. `createPeerConfigProfile` documents that its `roomTtlMs` default (7200000) is the TTL a room asks for before the relay clamps it, so a profile with the relay's values takes the `/config` `defaults`. The provider's 30-minute local expiry is documented as the fallback for a descriptor without `expiresAt`, which this relay always sends.
  - **Behavior change:** `parseInvitationUrl` returns the relay's room descriptor route `<server>/p/<roomId>/mcp` as `descriptorUrl` (the URL the relay reports and the provider shares; before, `<server>/p/<roomId>`, which the relay answers with 404), and `buildInvitationUrl` without a `descriptorUrl` builds `<server>/p/<roomId>/mcp#invite=<token>`. Both invitation forms, `/p/<roomId>` and `/p/<roomId>/mcp`, are still accepted.

- f167735: The open problems the protocol review left in the relay protocol spec are decided (relay protocol spec O-62 to O-77, chapter 10.1). Several change what an agent or a provider sees, so review the items marked **Behavior change**.

  - **Behavior change:** the relay checks a WebSocket `tools/call` without an id as it checks one with an id, and as it already checked one over HTTP: params without a non-empty string `name`, a catalog stamp in `params._meta` that is not the room's, and a tool the room's catalog does not list stop it before the provider. A notification has no one to answer, so one the relay refuses over WebSocket is dropped unanswered (over HTTP it still gets its 400, 409 or 400 under id null). Before, it reached the provider unchecked, and a provider that runs a message without an id could run a call made for another catalog (O-62, R-MCP-020, R-MCP-026, R-MCP-030).
  - **Behavior change:** the relay drops a `notifications/tools/list_changed` the provider sends instead of passing it to the agents. That notification is the relay's: it names the `catalogVersion` and `catalogHash` of a catalog the relay took, the stamp it checks every `tools/call` against, and a provider announces its catalog with `register`. The provider's other notifications and requests still reach the approved agents. The reference provider never sent one (O-63, R-SIG-004, R-MCP-041, R-CAT-008).
  - **Behavior change:** a room's expiry ends only the tickets still live (pending or approved). A session that was rejected or revoked, or whose approval request expired, before its room expired keeps that state and its `revokedAt` in `GET /p/:id/sessions/:sessionId`; before, the expiry reported every session of the room as `expired` (O-65, R-ROOM-035, R-ROOM-048).
  - The relay's credentials are bearer tokens it issues, not OAuth access tokens. This is now a rule of the spec, pinned by a test: its `WWW-Authenticate: Bearer` challenge carries no `resource_metadata`, and it serves no OAuth protected resource metadata (RFC 9728), authorization server metadata (RFC 8414) or OpenID Connect discovery (their `/.well-known/...` paths are 404). An MCP client sends the joined client token as a static `Authorization: Bearer` header and does not start an OAuth flow on a 401. No wire behavior changes (O-66, R-HTTP-019, R-PEER-053).
  - **Behavior change:** `PeerMcpSession` takes a message for the answer to one of its requests only as the relay does: `jsonrpc: "2.0"`, a string or number id, and a `result` or `error` member. A provider's request or notification that carries the id of a call in flight no longer ends that call or frees the relay slot the relay still counts for it (O-64, R-PEER-032).
  - **Behavior change:** `PeerMcpSession.request()` (and every call made through it) refuses a request whose id, as a string, is the id of one of the session's requests still in flight (waiting for its answer or for a relay slot, or holding a slot after its caller gave up) with `PeerMcpError` `DUPLICATE_REQUEST_ID` (`details: { method, id }`), without sending it, on every transport. `1` and `"1"` are one id here, since the session matches answers by `String(id)`. Before, the second request could take the first one's answer (over Streamable HTTP), or, over a relay socket, the relay's `DUPLICATE_REQUEST_ID` answer to it freed the first request's slot while the relay still counted it (O-64, R-PEER-032, R-PEER-035). A request is in flight, on every transport, from its `request()` call until its answer arrives or its connection ends, which includes its wait before a retry and lasts past its timeout: over Streamable HTTP, whose POST brings the answer, until that POST ends, and over a relay socket or a raw transport whose `send` returns before the answer, until the answer comes. So a request sent under the id of one that timed out is refused until that one's late answer has arrived, where before it could get that answer and lose its own (over Streamable HTTP, and over a raw transport whose `send` returns first), and a request waiting out a retryable refusal keeps its id, where before a request sent under it meanwhile made that request's own retry fail with `DUPLICATE_REQUEST_ID` (R-PEER-032, R-PEER-036). When a connection ends (`disconnect()`, a transport close, a frame that ends the session, a failed connect), every request gives back its id at once, even one whose `send` is still running, and that send, once it settles, touches nothing of a request sent under the id since; before, a request whose `send` was still running when `disconnect()` ran kept its id until that send settled, so a request under it on the reconnected session was refused with `DUPLICATE_REQUEST_ID` (R-PEER-032, R-PEER-045). Request ids and relay slots end with their connection: the session counts no such send on the next connection, of the same session or of another one handed the same transport. Keeping it off that connection is the transport's part (the `PeerMcpTransport` contract): a transport reused across connects (your own `transport`, or one your `transportFactory` hands out again) must not deliver on a later connection a message passed to `send()` while an earlier connection was live, and drops or fails such a send instead. The built-in WebSocket and Streamable HTTP transports are made for one connection each and, once closed, send nothing (`TRANSPORT_CLOSED`); the HTTP transport also reports nothing of a POST that ends after its close (O-73, O-74, R-PEER-031, R-PEER-032, R-PEER-035). A transport error (`onError`) or a `{type:'error'}` frame, which leaves the connection open, still rejects the requests waiting, but no longer gives back their ids and slots: a request sent keeps them until its answer arrives (over Streamable HTTP, until its POST ends), as after its timeout, where before a request sent under its id on the same connection could get its late answer (R-PEER-032, R-PEER-035, R-PEER-038). A transport you reuse across connects should not report an earlier connect's late answers through the next connect's callbacks, which the session cannot tell from that connection's own (R-PEER-031). A request waiting for a connect is ended at once, and gives back its id, by `disconnect()` (or a transport error or close), even while that connect is still getting its transport from a `transportFactory` or the `connect` of the caller's own transport, which cannot be cut short; before, it stayed pending until that returned (for good if it never did, as its timeout starts only once it is connected), and a request under its id on the reconnected session was refused with `DUPLICATE_REQUEST_ID` (R-PEER-045).
  - **Behavior change:** `PeerMcpSession.revoke()` sends one POST. Its body names the room id and room epoch only when the session knows them already; it no longer reads the session status or POSTs an `initialize` first to learn an unknown epoch, which the relay does not need (O-67, R-PEER-046).
  - **Behavior change:** the `onMessage` a session sets on a caller's `transport` that has none is now one per transport object: it delivers to the live connection that holds that transport, which is the one of the session that connected with it last, and to none while no connection holds it (after that session's `disconnect()`, say). A `PeerMcpService({ transport })` hands the same transport to every session it makes, so its `connect()`, `disconnect()`, `connect()` now gets the second session the transport's `ready` and answers, instead of a `TRANSPORT_TIMEOUT` while they went to the first session (O-69, R-PEER-031). A connect that `disconnect()` ended does not take it, even when that transport's `connect()` finishes after another session connected with the same transport; before, it took that `onMessage` back, and the other session stayed `connected` while its requests timed out (R-PEER-031, R-PEER-045). Nor does such a connect close that transport while a connection of any session handed it holds it, connected or still connecting; before, it closed it, so the other session stayed `connected` while every request failed, or, when the close was reported with code 1000, ended with `TRANSPORT_CLOSED` and did not connect again (R-PEER-045). A connection that has ended (its connect failed, the transport closed, or a frame ended its session) no longer holds the transport, so such a connect closes the transport it reopened when no live connection holds it; before, a session left on such a connection kept it open, for good once that session was abandoned (one whose `PeerMcpService.connect()` rejected, say) (R-PEER-045).
  - **Behavior change:** one transport object is held by one live connection at most, across every session. A connect that starts on a transport (your own `transport` as the connect starts, any other once the connect has it) ends the connection that held it until then: that session's requests are rejected with the new `PeerMcpError` code `TRANSPORT_SUPERSEDED` ("Peer transport was taken by another connection"), it leaves `connected` for `error`, and its requests fail with that error, without connecting again to take the transport back, until you call its `connect()`. Before, the earlier session stayed `connected` while it received nothing. So a session that `PeerMcpService({ transport })` replaced under the same key no longer holds the transport once the session replacing it connects, and a transport the service closes is not left open (O-76, R-PEER-031, R-PEER-055). A connection closes its transport when it ends, and only while it still holds it: a failed connect, a transport that closes and a frame that ends the session now close it at once, instead of at the next connect or `disconnect()`, and nothing else closes or keeps open a transport. So a transport that a connect `disconnect()` ended reopened late is closed by the connection holding it as that connection ends, even when its own connect fails; before, it was left open (O-75, R-PEER-045). A transport your `transportFactory` hands out again is held only once the connect it is handed to has it: a connect `disconnect()` ended that gets it first, while no connection holds it, closes it, and the factory hands it out again as it is (R-PEER-045). A frame that ends the session, or a close, reported while a connect is still getting its transport now fails that connect with that error, and later requests fail with it too; before, the connect ended `connected` once its ready wait timed out, and the next request timed out instead (O-77, R-PEER-031, R-PEER-038).
  - **Behavior change:** the provider answers nothing for a request of a connection that has ended or for a `tools/call` whose connection ended while it ran (a revocation, an expiry, a replaced or closed socket, `disconnect()`): the channel either would go on is already closed. The `PEER_SESSION_SUPERSEDED` and `OUTCOME_UNKNOWN` JSON-RPC errors it built for them never reached an agent and are gone, with their −32008 class; the agent learns of such a call from the error the relay ended its request with, and, with an AI run ledger, by calling again under the same `context.requestId`. That error is `SESSION_INVALID` for a revocation over HTTP (by the agent or the host), `ROOM_EXPIRED` or `ROOM_ROTATED` when the relay expired or rotated the room, and `PROVIDER_DISCONNECTED` when the provider socket closed first (the provider's own `disconnect()` or `revokeClient()`, a 4001 replacement, a dropped socket). A call whose connection ended while it waited for the ledger no longer runs, and is not answered from the ledger either: before, one the ledger held as `outcome-unknown` or durable was still answered `RECONCILIATION_REQUIRED` or with the replayed receipt, which went nowhere since its channel was closed. Nor does a call run, get an answer or leave a run behind when host code the provider calls before the host ends its connection with `disconnect()` (or `connect()` or `revokeClient()`, which call it): the host adapter's `getServerInfo`, which the provider asks as it reads the request, or a `subscribeAiRuns` listener told of the call's new run or of its action. Before, such a call still ran. No request of an ended connection is answered now, whatever its method and on either channel (relay socket or DataChannel): the provider checks a request's connection once its answer is ready, so host code it calls while handling the request (the host adapter's `getServerInfo`, or `listTools` for a DataChannel `tools/list` or `server/discover`; the ledger; a `subscribeAiRuns` listener) cannot make it answer a connection that ended meanwhile. Before, a `getServerInfo` that called `disconnect()` still had `ping`, `initialize`, `tools/list`, `server/discover` and an unknown method answered, and a request whose handling threw after its connection ended (a ledger lookup that failed, a host adapter that threw after `disconnect()`) was answered −32603 `Internal error`; none of it reached an agent, since the channel was closed. `PEER_SESSION_SUPERSEDED` stays the provider's session error after a 4001 close (O-68, R-PEER-012, R-PEER-013, R-PEER-016).
  - A call the host finished after its connection ended is now accounted for in its AI run unless `disconnect()` cleared the runs: its step (and its receipt's operation) is recorded and its action settled. Before, a session end that keeps the runs (a revocation, an expiry, a 4001 close) left the action in flight for good, so the run could not be rolled back (`AI run still has in-flight actions`) or evicted, and a rollback would not have undone the call. `AiRunController.hasAction(runId, requestId)` is new (O-68, R-PEER-016). A listener of the runs (`subscribeAiRuns`, `AiRunController.subscribe`) that throws no longer changes a call or its run: the controller drops the exception, as the provider does a session listener's, and still tells the other listeners, `clear` included. Before, one that threw as a call registered its action left the call unrun and answered −32603 with its action in flight for good, so the run could not be rolled back; one that threw as the provider settled a call the host ran failed the run with the listener's error and answered −32603 for a committed write, whose operation the run did not record, so a rollback did not undo it; and one that threw as the runs were cleared stopped `disconnect()` before it closed the socket. A listener whose `disconnect()` clears a call's run while the provider records the call now ends the recording there instead of throwing `Unknown AI run` (O-68, R-PEER-016).
  - **Behavior change:** the provider sends a request's answer in the turn it sees the request's connection still live. One network read can deliver several requests in one turn, and one of them may end the connection in a later turn, such as a `tools/call` whose `subscribeAiRuns` listener calls `disconnect()` as the call settles; a request of that read whose answer was ready first, a `ping` say, is now answered while the connection lasts or not at all. Before, its answer was sent a microtask after that check, on the channel of the connection that had ended meanwhile, which a real socket or DataChannel had already closed, so nothing reached the wire (O-70, R-PEER-012). A CRDT transport (`attachCrdtTransport`) whose `receiveVerified` or `receiveExternal` throws as the provider publishes an AI run to it no longer changes the run or what changed it: the provider logs the exception, as it already did wherever it introduces its agent to the transport, so a call the host ran is answered with its result and recorded in its run, a run the agent named is not failed, and `stopAiRun()` and `rollbackAiRun()` no longer throw. Before, a DataChannel `tools/call` whose write the host committed was answered −32603 `Internal error` and failed the run it named, so that run's next call got `AI_RUN_TERMINAL`, and `stopAiRun()` threw once it had stopped the run (O-71, R-PEER-013, R-PEER-016). R-PEER-013 now states what the provider already did: a `tools/call` is answered a JSON-RPC error only for invalid params (−32602) and for an unexpected exception outside the host call, such as a ledger lookup that fails (−32603 `Internal error`); whatever the host call gives is a `CallToolResult` (O-72).
  - **Behavior change:** `PeerMcpSession.connect()` shares a connect attempt only while that attempt's connection is live. Once the connection has ended before it connected (another connect took its transport, or a frame or a close ended it while the transport was still being obtained), `connect()` starts a new attempt instead of handing out the one that can only fail, and the ended attempt, when it fails, changes nothing of the new one. So a session whose transport another connect took takes it back with `connect()`; before, `connect()` returned the ended attempt until your transport's `connect` returned, and that attempt then failed with `TRANSPORT_SUPERSEDED`. A connect whose connection ended before it got its transport (a listener of the session whose connection it ended took the transport back with `connect()`, or a listener called `disconnect()`) now fails with that error without calling your transport's `connect(callbacks)` or your `transportFactory`, and a factory's connect whose connection ended as it took the transport fails at once instead of keeping that transport as the session's and waiting out the ready timeout. Before, the ended connect called your transport's `connect(callbacks)` last, so the transport reported through its dead callbacks and the session that took it back stayed `connected` while every request timed out. A connect that cannot give your transport an `onMessage` (a frozen object without one) now fails as any connect does: it ends its connection, closes the transport and leaves the session `error` with that exception. Before, the exception escaped the connect's own error handling, leaving the session `connecting` and its connection holding the transport, and the next connect then failed with `TRANSPORT_SUPERSEDED` (O-77, R-PEER-031, R-PEER-045).
  - The provider now logs (`console.warn`) the exception of a CRDT transport that throws as a DataChannel `tools/call` introduces its agent to it, as it does at every other place it tells the transport of its agent; before, that exception was dropped silently (O-71, R-PEER-016). The spec's R-PEER-016 now states when the provider publishes an AI run (a transport is attached, the session is `connected` and approved, and the room has the `mcp-crdt` capability or no room epoch) and through which method (`receiveVerified` when the room has an epoch and the transport has it, else `receiveExternal`); that behavior is unchanged.

- 13a88ee: The relay, provider and agent client now share one error model: one error name has one code everywhere, a refused credential is reported the same way on every route, a rotated room answers every lifecycle route alike, and a malformed path is a client error (relay protocol spec O-02, O-04, O-09, O-11, O-12, O-13, O-56, O-57). Several of these change what a peer sees, so review the items marked **Behavior change**.

  - The relay and the provider take the JSON-RPC code of every canonical error name from one internal table (`src/config/errors.ts`). A code is the error's class; the error is identified by its name (`message`, or `data.code`), and whether a request may be sent again only by `data.retryable`. The spec now lists which names share which class.
  - **Behavior change:** the provider answers a request it has not approved with `{code: -32053, message: "CLIENT_APPROVAL_REQUIRED"}`, the relay's code for that name, instead of −32003, which is the relay's code for a missing or invalid client token.
  - **Behavior change:** a relay lifecycle error body carries the `code` its JSON-RPC namesake has: `ROOM_NOT_FOUND` −32004, `ROOM_EXPIRED` −32056, `CLIENT_TOKEN_REQUIRED`/`CLIENT_TOKEN_INVALID` −32003, `CATALOG_UNAVAILABLE` −32090 and `BODY_CONSUMED` −32603. Before, these bodies had no `code`.

### Patch Changes

- 8462896: The relay bounds the work a provider's `register` frames cost. A frame identical to the last one the relay evaluated for the room, apart from `registerSeq`, is not normalized or hashed again while the room catalog is still the one that frame left: it gets the same answer (the same rejection under its own `registerSeq`, or none). Frames that change nothing (rejected as `CATALOG_INVALID` or `CATALOG_TOO_LARGE`, or carrying the catalog the room already holds) are evaluated at most 8 at once per room and then one per second; a frame that arrives while none is allowed waits, and the provider's next `register` replaces it, so the latest catalog is always evaluated and never refused for the rate. The budget belongs to the room, so a new provider socket does not reset it.

  The relay refuses an approved agent's `offer` whose `requestId` is over 1 KiB of JSON, the bound it already applies to JSON-RPC ids, with `{ type: "offer.refused", error: REQUEST_ID_TOO_LARGE }` (the id is not echoed) instead of forwarding an offer whose answer, which repeats the id, could never be sent.

  `upgradeWebSocket` treats a socket that is already ended by its peer (`readableEnded`) or no longer writable when it is called like one already destroyed: it sends no 101, destroys the socket, returns a `PeerSocket` whose `send` reports `'closed'`, and runs `onClose` once after returning. Such a socket used to stay half-open with `onClose` never called.
