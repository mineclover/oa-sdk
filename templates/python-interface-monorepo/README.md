# Python Interface Contract Workspace

uv workspace template for Python API contract management with Pydantic models,
OpenAPI artifacts, and CI gates.

The goal is not only to generate OpenAPI. The goal is to make API contracts easy
to review, change, and keep aligned with the running Python API.

## Architecture

The intended contract flow is:

```txt
Pydantic DTOs
  -> ContractRegistry / ContractSpec
  -> deterministic OpenAPI artifact
  -> drift / diff gates
  -> FastAPI runtime and generated clients
```

Responsibilities:

- Pydantic DTOs define request and response shapes.
- `ContractRegistry` is the intended authoring surface for models, endpoints,
  security schemes, reusable responses, examples, and targets.
- `ContractSpec` is the serializable contract document used by the CLI.
- OpenAPI JSON is a generated artifact. Do not treat it as the source of truth.
- Diff gates classify contract changes before merge.
- Drift gates compare the managed contract against the FastAPI runtime OpenAPI.

This boundary keeps implementation code, contract review, and generated artifacts
separate enough to manage independently.

## Workspace Layout

| Path | Purpose |
|---|---|
| `packages/interface-contracts` | Core contract models, Pydantic schema extraction, OpenAPI emit, and breaking diff primitives. |
| `packages/interface-cli` | `oa-contract` CLI for validation, OpenAPI artifact generation, and compatibility checks. |
| `apps/example-api` | FastAPI example that shares Pydantic DTOs and contract definitions with the tooling. |

Future adapters should be added as workspace members under `packages/*`, for
example `packages/interface-fastapi`.

## Management Model

Recommended project layout for a real API:

```txt
apps/example-api/src/example_api/
  models.py       # Pydantic DTOs
  contracts.py    # ContractRegistry or ContractSpec
  main.py         # FastAPI app and route handlers

contracts/<api>/
  contract.json             # optional serialized ContractSpec snapshot
  openapi.json              # generated default OpenAPI artifact
  openapi.public.json       # generated target-specific artifact, if used
  compatibility-report.json # generated review output, if stored
  baselines/
    v1.contract.json        # previous released contract snapshots
```

Rules:

- Keep DTOs in Pydantic models.
- Register schemas and endpoints in the contract layer.
- Keep route handlers in the app layer.
- Generate `contracts/<api>/openapi.json` from the contract layer.
- Review contract source changes or `contract.json` snapshots, not only
  generated OpenAPI changes.
- Fail CI when generated artifacts are stale, breaking changes are unapproved,
  or FastAPI runtime drift is detected.

## Source Of Truth And Artifacts

Pick one contract authoring source for each API:

- Code-first source of truth: Pydantic DTOs plus `ContractRegistry` definitions
  loaded from `module:attr`, such as `example_api.main:contract`.
- File-first source of truth: a checked-in `ContractSpec` JSON file, such as
  `contracts/example-api/contract.json`.

The generated files are review evidence, not authoring surfaces:

- `contracts/<api>/contract.json` is generated by `oa-contract snapshot`
  when the working source of truth is a module reference.
- `contracts/<api>/openapi.json` is generated by `oa-contract emit-openapi`.
- `contracts/<api>/openapi.<target>.json` is generated with `--target`.
- `compatibility-report.json` or Markdown review reports are generated by
  `oa-contract review`.

Do not manually edit generated OpenAPI to fix CI. Change the DTOs, registry
metadata, target policy, or FastAPI route metadata, then regenerate artifacts.
If both a module reference and `contract.json` exist for one API, keep the
module reference as the working source and refresh `contract.json` as a
serialized review snapshot.

## Existing FastAPI Migration

The migration path is incremental. You do not need to rewrite an existing API.

1. Keep existing FastAPI handlers and Pydantic request/response models in
   place.
2. Add a `contracts.py` module beside the app with a `ContractRegistry`,
   security schemes, reusable error responses, examples, and model
   registrations.
3. Add `@registry.route(...)` beside one existing FastAPI route decorator.
   Match the existing `path`, HTTP method, `operation_id`, request model,
   response model, documented statuses, and security dependencies.
4. Point validation, drift, and artifact checks at the module that imports the
   decorated routes, for example `example_api.main:contract`.
5. Emit `contracts/<api>/openapi.json` and compare the generated artifact with
   the current FastAPI OpenAPI.
6. Resolve drift route by route. Keep adding endpoints until the managed
   contract covers the public surface you want CI to protect.
7. Add the pytest helper or shell command gates to CI.
8. Add target policies only after the base contract is aligned. Start with
   `public` and introduce `admin` or `internal` slices when the shared DTO
   boundaries are clear.

For large services, migrate one router at a time. The drift command will report
runtime-only routes as `route-missing-in-contract`; treat those as the backlog
for the next migration slice unless they should remain outside the managed API
surface.

## CI Examples

GitHub Actions:

```yaml
name: contract-governance

on:
  pull_request:
  push:
    branches: [main]

jobs:
  contracts:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true

      - run: uv lock --check
      - run: uv sync --locked
      - run: uv run pytest
      - run: uv run ruff check .
      - run: uv run mypy

      - run: uv run --package oa-interface-cli oa-contract snapshot example_api.main:contract --output contracts/example-api/contract.json
      - run: uv run --package oa-interface-cli oa-contract validate example_api.main:contract
      - run: uv run --package oa-interface-cli oa-contract check-artifact example_api.main:contract contracts/example-api/openapi.json
      - run: uv run --package oa-interface-cli oa-contract drift --app example_api.main:app --contract example_api.main:contract --format markdown
```

If the repository stores base and head contract snapshots, add the review gate:

```yaml
      - run: |
          uv run --package oa-interface-cli oa-contract review \
            contracts/base.contract.json \
            contracts/head.contract.json \
            --app example_api.main:app \
            --artifact contracts/example-api/openapi.json \
            --format markdown
```

Pre-commit example:

```yaml
repos:
  - repo: local
    hooks:
      - id: ruff-check
        name: ruff check
        entry: uv run ruff check .
        language: system
        pass_filenames: false

      - id: contract-validate
        name: contract validate
        entry: uv run --package oa-interface-cli oa-contract validate example_api.main:contract
        language: system
        pass_filenames: false

      - id: contract-artifact
        name: contract artifact freshness
        entry: uv run --package oa-interface-cli oa-contract check-artifact example_api.main:contract contracts/example-api/openapi.json
        language: system
        pass_filenames: false
```

Keep pre-commit focused on fast checks. Run pytest, mypy, drift, review, and
target-specific artifact checks in CI when they are too slow for local commits.

## Commands

Install and run workspace checks:

```bash
uv sync
uv run pytest
uv run ruff check .
uv run mypy
```

Run the CLI:

```bash
uv run --package oa-interface-cli oa-contract --help
```

When endpoints are registered with `@registry.route(...)` in `main.py`, point
CLI commands and tests at `example_api.main:contract`. Importing `main.py`
materializes route decorator registrations before the contract is serialized.

Validate a serialized contract or a registry reference:

```bash
uv run --package oa-interface-cli oa-contract validate contracts/example-api/contract.json
uv run --package oa-interface-cli oa-contract validate example_api.main:contract
```

Write a deterministic machine-readable contract snapshot:

```bash
uv run --package oa-interface-cli oa-contract snapshot \
  example_api.main:contract \
  --output contracts/example-api/contract.json
```

The snapshot wraps the serialized `ContractSpec` with deterministic toolkit
version metadata. The same `contract.json` file can be passed to `validate`,
`diff`, `emit-openapi`, and `review` without importing application code.

Emit deterministic OpenAPI:

```bash
uv run --package oa-interface-cli oa-contract emit-openapi \
  contracts/example-api/contract.json \
  --output contracts/example-api/openapi.json

uv run --package oa-interface-cli oa-contract emit-openapi \
  example_api.main:contract \
  --output contracts/example-api/openapi.json

uv run --package oa-interface-cli oa-contract emit-openapi \
  example_api.main:contract \
  --target public \
  --output contracts/example-api/openapi.public.json
```

Emitted OpenAPI includes `x-oa-contract-hash`, a SHA-256 hash derived only from
the serialized contract spec. It is stable across repeated runs for the same
contract and should change when the managed contract changes. When `--target`
is provided, the artifact includes only endpoints assigned to that target and
schemas reachable from those endpoints.

Check that the checked-in OpenAPI artifact is fresh:

```bash
uv run --package oa-interface-cli oa-contract check-artifact \
  contracts/example-api/contract.json \
  contracts/example-api/openapi.json

uv run --package oa-interface-cli oa-contract check-artifact \
  example_api.main:contract \
  contracts/example-api/openapi.json \
  --format json
```

Use `contracts/<api>/openapi.json` as the generated artifact path in CI. The
check parses the existing artifact and compares it with freshly emitted managed
OpenAPI, so formatting changes do not cause false failures.

Review breaking changes:

```bash
uv run --package oa-interface-cli oa-contract diff \
  contracts/base.contract.json \
  contracts/head.contract.json \
  --fail-on-breaking
```

Run the example FastAPI app:

```bash
uv run --package example-api python -m example_api.main
```

Target drift command for the FastAPI adapter lane:

```bash
uv run --package oa-interface-cli oa-contract drift \
  --app example_api.main:app \
  --contract example_api.main:contract \
  --format text
```

Use `--format json` for machine-readable CI details or `--format markdown` for
pull request summaries.

Generate a combined contract review report for pull requests:

```bash
uv run --package oa-interface-cli oa-contract review \
  contracts/base.contract.json \
  contracts/head.contract.json \
  --app example_api.main:app \
  --artifact contracts/example-api/openapi.json \
  --format markdown

uv run --package oa-interface-cli oa-contract review \
  contracts/base.contract.json \
  contracts/head.contract.json \
  --app example_api.main:app \
  --artifact contracts/example-api/openapi.json \
  --format json
```

The review report combines the contract diff, head-contract validation,
FastAPI drift, and OpenAPI artifact freshness. It recommends `APPROVE` when
all checks are clean, `COMMENT` for non-breaking or incomplete review signals,
and `REQUEST_CHANGES` for breaking changes, validation errors, drift, or stale
artifacts.

## Pytest Integration

Use the assertion helpers when an existing service already has pytest in CI and
does not need a separate shell script for each contract gate.

```python
from pathlib import Path

from oa_interface_contracts import (
    assert_contract_valid,
    assert_openapi_artifact_current,
)
from oa_interface_fastapi import assert_no_fastapi_drift


OPENAPI_ARTIFACT = Path("contracts/example-api/openapi.json")


def test_contract_gate() -> None:
    assert_contract_valid("example_api.main:contract")
    assert_no_fastapi_drift("example_api.main:app", "example_api.main:contract")
    assert_openapi_artifact_current(
        "example_api.main:contract",
        OPENAPI_ARTIFACT,
    )
```

The helpers also accept direct objects, which is useful when tests already
import the app or contract:

```python
from example_api.main import app, contract


def test_contract_gate_direct_objects() -> None:
    assert_contract_valid(contract)
    assert_no_fastapi_drift(app, contract)
```

Failed assertions include the validation issue code, drift issue code, affected
operation or artifact path, and the concise artifact drift summary used by the
CLI.

## Adding Models And Endpoints

1. Add or update the Pydantic DTO.
2. Register the model schema in `ContractRegistry` or `ContractSpec.schemas`.
   Use `audience="public"`, `audience="admin"`, `audience="internal"`, or
   `audience="shared"` when a model should be limited or explicitly shared
   across target-specific artifacts.
3. Register reusable security schemes, error responses, and examples when the
   endpoint needs them. Use `responses={...}` for additional success statuses.
4. Configure target policies with `required_error_responses=[...]` and
   `public=True` when public contract leakage checks should apply.
5. Register the endpoint with `registry.endpoint(...)`, or use
   `@registry.route(...)` beside the framework route decorator.
6. Add or update the FastAPI route with matching request and response models.
7. Emit OpenAPI and inspect the artifact diff.
8. Run validation, diff, drift, and workspace checks.

In the example app, DTOs live in `models.py`, the managed contract lives in
`contracts.py`, and FastAPI routes live in `main.py`. Keep that separation in
real services so implementation changes and contract changes can be reviewed
independently.

```python
registry.bearer_security_scheme(
    "BearerAuth",
    bearer_format="JWT",
    description="JWT bearer token.",
)
registry.public_target(
    description="Public user-management API.",
    required_error_responses=["Unauthorized"],
)
registry.model("CreateUser", CreateUser, audience="public")
registry.model("ErrorResponse", ErrorResponse, audience="public")
registry.model("User", User, audience="public")
registry.error_response(
    "Unauthorized",
    status_code=401,
    description="Authentication required.",
    model="ErrorResponse",
)

@registry.route(
    method="post",
    path="/users",
    operation_id="create_user",
    request_model="CreateUser",
    response_model="User",
    security=["BearerAuth"],
    error_responses=["Unauthorized"],
    targets=["public"],
)
@app.post(
    "/users",
    response_model=User,
    operation_id="create_user",
    responses={401: {"model": ErrorResponse, "description": "Authentication required."}},
)
def create_user(body: CreateUser) -> User:
    ...
```

Use `api_key_security_scheme(...)`, `oauth2_security_scheme(...)`,
`open_id_connect_security_scheme(...)`, and `mutual_tls_security_scheme(...)`
for the other OpenAPI security scheme types. Endpoint `security=[...]` accepts
plain scheme names for empty-scope requirements or OpenAPI requirement mappings
such as `{"OAuth2": ["users:read"]}`.

Multi-status success responses can be declared without giving up reusable error
responses:

```python
registry.endpoint(
    method="post",
    path="/users",
    operation_id="create_user",
    request_model="CreateUser",
    responses={
        201: {
            "description": "User created.",
            "model": "User",
            "examples": ["created_user_response"],
        },
        202: {
            "description": "User creation accepted.",
            "model": "Job",
        },
    },
    error_responses=["Unauthorized"],
)
```

## Breaking Change Review

Treat these as breaking until proven otherwise:

- endpoint removed
- method or path changed
- `operation_id` changed
- request model changed
- response model changed
- required request field added
- response field removed
- response field type narrowed
- status code removed
- security requirement strengthened

Non-breaking changes usually include:

- endpoint added
- optional request field added
- optional response field added
- summary or description changed
- tag added
- additional success status documented

Every pull request that changes API contracts should include:

- the contract diff output
- whether `--fail-on-breaking` passed
- the generated OpenAPI artifact diff
- the FastAPI drift result

Intentional breaking changes should be explicit, not hidden. Use this process:

1. Run `oa-contract diff --fail-on-breaking` and copy the breaking change list
   into the pull request.
2. Document why the change is intentional, which clients or targets are
   affected, and the migration path for adopters.
3. Update released contract baselines under `contracts/<api>/baselines/` when
   the new contract becomes the baseline for future diffs.
4. Regenerate OpenAPI artifacts from the new source of truth.
5. Require human approval for the breaking change before merging. Do not bypass
   the gate by editing generated OpenAPI or deleting the old baseline.

## FastAPI Drift Handling

FastAPI can generate OpenAPI from route decorators and Pydantic models. This is
useful, but it should not silently replace managed contracts.

The drift gate should compare:

- route exists in FastAPI and contract
- method and path match
- `operationId` matches
- request body schema matches
- response schema and documented status codes match
- tags and summaries are intentionally aligned
- security requirements match

If FastAPI exposes a route not declared in the contract, either add it to the
contract or explicitly exclude it from public contract checks. If the contract
declares a route not implemented by FastAPI, block the change until the handler
or contract is corrected.

Known framework drift should be resolved or suppressed at the narrowest layer:

- FastAPI's automatic 422 validation response is suppressed automatically only
  when it has the framework validation-error shape. If a 422 response is part
  of your API contract, register it as an explicit reusable error response.
- Pydantic `$defs` references and managed governance schema extensions such as
  `x-oa-audience`, `x-oa-targets`, and internal-only markers are normalized by
  the FastAPI adapter. They should not require local allowlists.
- Resolve operation drift by aligning `operation_id`, `response_model`,
  `responses={...}`, dependencies/security metadata, tags, and status codes
  on the FastAPI route with the registry endpoint declaration.
- Resolve schema drift by changing the shared Pydantic DTO first. If runtime
  and contract use different DTO classes intentionally, register the contract
  DTO explicitly and document why the runtime shape is still equivalent.
- Resolve runtime-only route drift by adding the route to the managed contract
  or by moving the route outside the FastAPI app instance used for contract CI
  when it is health, metrics, or framework infrastructure rather than API
  surface.
- Add adapter-level normalization only for repeatable framework output with a
  focused regression test. Avoid broad per-route suppressions because they hide
  real contract drift.

## Acceptance Criteria

Team implementation should be considered complete when:

- `ContractRegistry` exists as the preferred authoring API and can emit a
  deterministic `ContractSpec`.
- Duplicate schema names, duplicate endpoints, duplicate operation IDs, missing
  model references, invalid path parameter references, missing target-required
  error responses, and public/internal leakage are rejected.
- `oa-contract validate` accepts valid contract JSON or `module:attr` registry
  references and fails invalid contracts.
- `oa-contract snapshot` writes a deterministic `contract.json` snapshot with
  toolkit version metadata.
- `oa-contract emit-openapi` accepts valid contract JSON or `module:attr`
  registry references and produces stable OpenAPI 3.1 JSON with sorted output
  plus contract-derived hash metadata.
- `oa-contract check-artifact` compares `contracts/<api>/openapi.json` with
  freshly emitted managed OpenAPI and exits non-zero when the artifact is stale.
- `oa-contract diff --fail-on-breaking` exits non-zero for breaking changes.
- `oa-contract drift --app module:app --contract module:contract` compares
  FastAPI runtime OpenAPI against the managed contract and exits non-zero on
  drift.
- `uv run pytest`, `uv run ruff check .`, and `uv run mypy` pass from the
  workspace root.
- README examples match the implemented CLI behavior.

## uv Workspace Notes

This template follows uv workspace conventions: every workspace member has its
own `pyproject.toml`, and dependencies between workspace members use
`[tool.uv.sources]` with `workspace = true`.
